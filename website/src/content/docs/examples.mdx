The repository has six samples. They answer different questions, so they are kept separate:
the minimal sample is what you **copy** to start a game, and LineSweeper is what you **read** to
see what a finished one looks like. Three focused examples teach collision, audio and local
multiplayer, and the components are pieces you copy one at a time. All build with the engine.

## The minimal sample: the one you copy

`samples/minimal` is about 760 lines, comments and tests included. It opens a 1280×720 window with a line
of text that circles a point you move with a gamepad stick, the arrow keys or WASD. Press B or
Escape and it asks, in a second screen on top of the first, whether you really want to quit.

That is small, but it is a complete game on the engine. It has a first state, a second state
pushed on top that returns a result, a scene that owns what is on screen, input from three kinds
of device, content named in a manifest, rules in a library its tests run without a window, a
start-up check, and the build file that copies that content beside the executable or packs it
into a browser build.

| File | What it shows |
| --- | --- |
| <RepoLink path="samples/minimal/main.cpp">`main.cpp`</RepoLink> | Window options, loading the content manifest, handing the engine its first state, and `--smoke-test`, which runs that state hidden for 30 frames and quits. |
| <RepoLink path="samples/minimal/main_web.cpp">`main_web.cpp`</RepoLink> | The same, as a browser's entry point, with the `Application` kept in a static. |
| <RepoLink path="samples/minimal/states/hello_state.cpp">`states/hello_state.cpp`</RepoLink> | A scene with two labels and one view, input from a pad and a keyboard at once, and a marker on every touch point. |
| <RepoLink path="samples/minimal/rules/motion.cpp">`rules/motion.cpp`</RepoLink> | The game's rules: two devices' directions summed and clamped, and a transform built each step. They link the engine's maths and nothing else of it. |
| <RepoLink path="samples/minimal/tests/motion_tests.cpp">`tests/motion_tests.cpp`</RepoLink> | doctest cases that run the rules with no window and no device. |
| <RepoLink path="samples/minimal/states/confirm_state.cpp">`states/confirm_state.cpp`</RepoLink> | A state pushed above another that hands a `bool` back when it closes. |
| <RepoLink path="samples/minimal/content/manifest.json">`content/manifest.json`</RepoLink> | The one font the sample uses, named once and resolved to a handle at load. |
| <RepoLink path="samples/minimal/CMakeLists.txt">`CMakeLists.txt`</RepoLink> | The whole build file: sources, the rules library and its test, the start-up check, the engine's two libraries, the content copied beside the executable or packed into the page, and the install rules that stage the [release folder](/docs/guides/windows-release/). |

## LineSweeper: the one you read

`samples/linesweeper` is a falling-block game with seven pieces, a next queue, a hold slot, hard
drop, wall kicks, T-spins and back-to-back scoring, and a field of up to ten thousand particles
that bursts when a piece locks, when lines clear and when the game ends. It is about 5,000 lines,
with about 2,700 more of tests, and it is there to show what a whole game on Labrador looks like
and what it costs.

[Play LineSweeper in a desktop browser](https://mattharding.dev/demo/linesweeper/), before you
build anything: the hosted demo downloads the game only when you click, and plays with a keyboard.
Phones are a planned phase, so a phone gets a poster and a recording of the game to tap and
watch, not the game itself, until real iPhone checks and the host page's phone layout pass.
Android remains unverified.

It is built in three layers, and the walls between them are the point:

- **`rules/`**, the simulation: a static library that links nothing from the engine, so the
  whole game can be played and checked inside the test suite with no window.
- **`presentation/`** reads a match and draws it. It may read the rules' data but may not call
  the functions that change it.
- **`states/`** is the only layer that sees both, and where key presses become moves.

Start with its <RepoLink path="samples/linesweeper/README.md">design notes</RepoLink>. They
record every decision in the sample with its reasons, including the ones that went the other
way. Then read the code in this order:

1. <RepoLink path="samples/linesweeper/rules/world.h">`rules/world.h`</RepoLink>: the whole match as one 276-byte value, and the four compile-time checks that keep it one.
2. <RepoLink path="samples/linesweeper/rules/tick.h">`rules/tick.h`</RepoLink>: the one function that advances the game by a step.
3. <RepoLink path="tests/linesweeper/replay_tests.cpp">`tests/linesweeper/replay_tests.cpp`</RepoLink>: whole matches played, recorded and replayed with no window.
4. <RepoLink path="samples/linesweeper/presentation/particles.h">`presentation/particles.h`</RepoLink>: ten thousand particles behind one game object.
5. <RepoLink path="samples/linesweeper/states/play_state.cpp">`states/play_state.cpp`</RepoLink>: keyboard and gamepad bindings, and the frame that ties the layers together.

To run the match replays, follow the
<RepoLink path="samples/linesweeper/README.md" hash="running-the-rules-tests">rules-test commands and prerequisites</RepoLink>.
They build the rules test target without the engine library, while the root configure still
needs the engine's toolchain and dependencies. The same section records the known hosts and presets.

## Components: the pieces you copy

`samples/components` holds small pieces of game code: menu widgets to style and
animation playback policy to adapt. Each is a header and a source file with its
own tests, which you copy into your game and change as you like. They are not a
library, so nothing promises to keep your copy compatible,
and the engine does not know they exist. A gallery shows them all on one screen.

| Component | What it is |
| --- | --- |
| <RepoLink path="samples/components/option_row.h">Option row</RepoLink> | A label and a value picked from a fixed list with left and right, such as a difficulty or a window mode. It wraps or stops at the ends. |
| <RepoLink path="samples/components/slider.h">Slider</RepoLink> | A label, a bar and a number for an integer in a range, such as a volume. It clamps at the ends and never wraps. |
| <RepoLink path="samples/components/nine_slice.h">Nine-slice</RepoLink> | One small image drawn at any size with its corners kept, such as a panel or a button background. |
| <RepoLink path="samples/components/animation_preview.h">Animation preview</RepoLink> | A value that keeps elapsed time, loops or finishes a named strip, and restarts. Drawing reads the current frame. |

A component reads no input, because bindings are your game's decision. For
menu rows, your page moves the cursor with a `FocusGroup` and passes left and
right to the focused row. The gallery finds that row by comparing pointers,
since the page already holds every row it built:

<SourceFile
	path="samples/components/gallery_state.cpp"
	from="bool GalleryState::adjust_focused(Direction direction)"
	to="}"
/>

A compound that every game ends up copying unchanged is a candidate for the engine's widget set.
One that every game edits stays a component. The
<RepoLink path="samples/components/README.md">components README</RepoLink> explains the rule, and
the <RepoLink path="docs/design/PHILOSOPHY.md">design philosophy</RepoLink> states it.

### Playing an animation strip

The gallery owns two `AnimationPreview` values over the same original atlas:
one loops and one holds its final frame. R or gamepad X restarts both. They do
not take focus or change the settings rows. The gallery updates their clocks
once per tick, then draws them through the scene's overlay with its fitted
camera and viewport:

<SourceFile
	path="samples/components/gallery_state.cpp"

The [Sprites and text guide](/docs/guides/sprites-and-text/#sprites-from-a-sheet)
quotes the named strip resolution, timing policy and public `frame_rect` draw
path. The sample includes its DDS/JSON pair, original MIT artwork provenance,
and in-memory timing plus native-null drawing tests. Actual rendered-frame
review remains separate from those headless checks.

## Running them

The samples are in the engine's folder, not in your game, and your game's build does not make
them. [Run the samples](/docs/guides/samples/) builds them from a starter project, in
`C:\dev\mygame\external\labrador`, or from a clone, where
[Build Labrador](/docs/get-started/build-labrador/) has already built them. From that folder,
they are at:

```text
out\build\x64-debug\samples\minimal\MinimalSample.exe
out\build\x64-debug\samples\linesweeper\LineSweeperSample.exe
out\build\x64-debug\samples\collision\CollisionSample.exe
out\build\x64-debug\samples\audio\AudioSample.exe
out\build\x64-debug\samples\local_multiplayer\LocalMultiplayerSample.exe
out\build\x64-debug\samples\components\ComponentsGallery.exe
```

Each copies its content beside its executable, so you can start it from anywhere. That page
also says how long the build takes, how to quit each sample and what each failure means. Under a
`wasm-*` preset each is a page instead, such as
`out\build\wasm-debug\samples\collision\CollisionSample.html`, with its content packed into
the module. [Run the samples](/docs/guides/samples/#in-a-browser) builds them for the browser
from the same folder and serves them, step by step, once
[Build for the browser](/docs/guides/browser/#install-emscripten) has installed Emscripten.
[Put your game on a web host](/docs/guides/web-host/) says what a host must send.
