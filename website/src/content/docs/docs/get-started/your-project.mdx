Starting a game on Labrador means copying the minimal sample and owning everything inside it.
Your project is its own repository. Labrador sits inside it as a Git submodule, pinned to the
commit you chose, and is built as part of your build.

This page calls the project `mygame`. Use your own name wherever that appears. The `name` in
`vcpkg.json` takes only lowercase letters, digits and hyphens, so a project called `MyGame` is
`mygame` there; vcpkg stops configure with `"MyGame" is not a valid package name` otherwise.

When you have finished, the project looks like this:

<FileTree>
- mygame/
  - CMakeLists.txt your build, which builds Labrador first
  - CMakePresets.json
  - vcpkg.json the engine's dependencies, at the engine's versions
  - .gitignore
  - external/
    - labrador/ the engine, as a submodule
  - game/
    - CMakeLists.txt
    - main.cpp
    - content/
    - rules/ the game's rules, which its tests run without a window
    - states/
    - tests/
</FileTree>

<Steps>

1. **Make the repository.** In the x64 Native Tools Command Prompt:

   ```bat
   cd C:\dev
   mkdir mygame
   cd mygame
   git init
   ```

2. **Add Labrador as a submodule, and check out a release:**

   ```bat
   git submodule add https://github.com/matt439/Labrador.git external/labrador
   git -C external/labrador checkout v0.1.0
   ```

   `v0.1.0` is the first release. Check out the latest tag, which
   `git -C external/labrador tag --list "v*" --sort=-v:refname` lists newest first, if there is a newer one. Your repository
   now records exactly which commit of Labrador it builds against, and moving to a newer tag
   is a change you make deliberately and commit, after reading what
   [CHANGES.md](https://github.com/matt439/Labrador/blob/master/CHANGES.md) says changed
   between the two. This site documents `master`, which can be ahead of the newest tag, and
   CHANGES.md's *Unreleased* heading, when it has one, lists what `master` has that the tag
   does not.
   Anyone cloning your project needs `git clone --recurse-submodules` to get the engine too.

3. **Copy the minimal sample** into a folder called `game`:

   ```bat
   xcopy external\labrador\samples\minimal game /E /I
   ```

4. **Point its includes at the new folder.** Includes in Labrador are written from the root of
   the repository, so the sample names its own headers as `samples/minimal/...`. In your project
   they are under `game/`. Change these lines:

5. **Replace `game\CMakeLists.txt`** with this:

   <Code code={gameCMake} lang="cmake" title="game/CMakeLists.txt" />

   It is the Windows half of the sample's build file, with its names changed: the program is
   `MyGame`, the rules library `MyGameRules`, the tests `MyGameTests` and `MyGameSmokeTests`, and
   the content target `game_content`. One line is new. `target_include_directories` makes the
   folder above `game` the place your includes start from, for the rules and for everything that
   links them, which the sample did not need because Labrador's root already was.

   Two tests come with it. `MyGameTests` runs the rules in `game\rules` with no window and no
   graphics device. `MyGameSmokeTests` starts the game hidden with `--smoke-test`, lets it draw
   a few frames and quits, so a change that stops the game starting fails a test rather than
   your next launch. [Test your game](/docs/guides/testing/) says how both work and how to add
   your own.

6. **Add the project's own build files** to the `mygame` folder.

   <Code code={rootCMake} lang="cmake" title="CMakeLists.txt" />

   `enable_testing()` makes your tests ctest's. `add_subdirectory(external/labrador)` builds the
   engine library and defines the targets your build links: `LabradorEngine`; `MattMath`, the
   engine's maths on its own, which the rules library links instead of the whole engine; and
   `labrador_settings`, which applies the engine's compiler settings to your code too, warnings
   as errors included. Do not define your own `labrador_settings`; CMake stops at a second target
   with the same name.

   dependencies itself, and `doctest`, the test framework your tests use. The
   `builtin-baseline` is Labrador's own, which pins them to the versions the engine is built and
   tested with.

7. **Build, test and run it:**

   ```bat
   cmake --preset x64-debug
   cmake --build --preset x64-debug
   ctest --preset x64-debug
   out\build\x64-debug\game\MyGame.exe
   ```

   ctest runs your two tests and reports `100% tests passed, 0 tests failed out of 2`. The
   window is the minimal sample's, because so far the game is the minimal sample. The
   configure step installs the dependencies for this project; vcpkg reuses what it built for
   Labrador, so it is quicker than the first time.

8. **Commit it:**

   ```bat
   git add .
   git commit -m "Start from Labrador's minimal sample"
   ```

</Steps>

<Aside title="Only the library is built">
Because Labrador is not the top-level project here, its tests, benchmarks and samples are left
out of your build. You get the engine and nothing else, and your ctest runs your game's tests
and none of Labrador's. To check every push in GitHub Actions, copy the workflow in
[Check your game in CI](/docs/guides/ci/).
</Aside>
