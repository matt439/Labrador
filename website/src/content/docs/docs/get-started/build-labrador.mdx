You build Labrador on its own first. That proves the tools work before your own project adds
anything, and it builds the samples you will look at next.

<Steps>

1. **Clone the repository** into your projects folder:

   ```bat
   cd C:\dev
   git clone https://github.com/matt439/Labrador.git
   cd Labrador
   ```

2. **Configure the build:**

   ```bat
   cmake --preset x64-debug
   ```

   A *preset* is a named configuration in the repository's `CMakePresets.json`. `x64-debug` is a
   64-bit debug build using the Direct3D 11 renderer, with its output in `out\build\x64-debug`.

   The first time you run this, vcpkg downloads and builds Labrador's dependencies: DirectX Tool
   Kit and the DirectXMath library it uses, the XAudio2 redistributable, the doctest test
   framework and the lodepng image library. It may also download a CMake and a PowerShell of its
   own if it finds Visual Studio's unsuitable. With nothing cached, the first configure downloads
   about 330 MB in all.
   On a fast desktop with an empty cache that configure took 2 minutes 17 seconds, 1.2 minutes of
   it vcpkg building seven packages, and vcpkg keeps the results, so later configures are quick.
   The whole build folder, `out`, comes to about 1.3 GB once the next two steps have run.

3. **Build it:**

   ```bat
   cmake --build --preset x64-debug
   ```

   This builds the engine, all six samples, the tests and the benchmarks, which took 21 seconds
   on the same desktop. Warnings are errors in every Labrador build, so a successful build has
   none.

4. **Run the tests:**

   ```bat
   ctest --preset x64-debug
   ```

   Eighteen test programs, the minimal sample's start-up check and the benchmarks run, and ctest
   should report `100% tests passed, 0 tests failed out of 20`. One of them, `RenderPixelTests`,
   draws real frames through Direct3D and compares them with reference images, so a pass also
   tells you the renderer works on your machine.

</Steps>

## Other configurations

The `x64-*` presets are available only when CMake runs on Windows. The `wasm-*`
presets have no host restriction, but building them on Linux or macOS is unverified.
They still require the [browser toolchain](/docs/guides/browser/). There is no native
Linux or macOS window implementation; [Platform support](/why/#platform-support)
states the supported targets and the port plans.

The repository has a debug and a release preset for each renderer. Swap the preset name in all
three commands to use one:

| Preset | Renderer |
| --- | --- |
| `x64-debug`, `x64-release` | Direct3D 11 |
| `x64-debug-d3d12`, `x64-release-d3d12` | Direct3D 12 |
| `x64-debug-gl`, `x64-release-gl` | OpenGL 3.3 |
| `x64-debug-vulkan`, `x64-release-vulkan` | Vulkan, which needs the Vulkan SDK |
| `x64-debug-null`, `x64-release-null` | None: records what it was asked to draw, for testing on machines without a graphics card |

The renderer is chosen when you configure rather than when the game starts. Asking for one that
was not built is a link error, not a crash on the first frame. A game you ship is built with
one renderer too: [Which renderer to ship](/docs/guides/windows-release/#which-renderer-to-ship)
recommends Direct3D 11 and says what a machine that refuses it shows.

## If something fails

<Aside type="caution" title="Filename too long">
The clone was made in a folder whose path is too long. Delete the partial clone and clone again
into a shorter folder. `git config --global core.longpaths true` would let the clone finish, but
the build would then fail in the same folder. See
[Choose a short folder](/docs/get-started/prerequisites/#choose-a-short-folder).
</Aside>

<Aside type="caution" title={"fatal error C1083: Cannot open compiler generated file: '': Invalid argument"}>
The `Labrador` folder's path is too long for the compiler, and configure will have warned about
`CMAKE_OBJECT_PATH_MAX` first. Long paths enabled in Windows and in Git do not help the compiler.
Clone into a folder whose path is under 100 characters, or give your folder a drive letter as in
[Keeping a deep folder](/docs/get-started/prerequisites/#keeping-a-deep-folder), and build there.
</Aside>

<Aside type="caution" title="cmake, cl or fxc is not recognised">
The command prompt is not the x64 Native Tools Command Prompt. Open that one and run the
command again from the `Labrador` folder.
</Aside>

<Aside type="caution" title={'Could not find toolchain file: "/scripts/buildsystems/vcpkg.cmake"'}>
`VCPKG_ROOT` is not set, so the preset's path to vcpkg starts with nothing. The errors about
Ninja and the compiler that follow it are consequences of the first one. Set `VCPKG_ROOT` as in
step 4 of [Install the tools](/docs/get-started/prerequisites/), delete the half-configured
`out\build\x64-debug` folder, and configure again.
</Aside>
