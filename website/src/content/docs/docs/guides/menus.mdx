A Labrador menu is a [state](/docs/concepts/states/) with a scene of **widgets** in it and a
**focus group** that knows which widget the cursor is on. The engine solves the two things every
controller-driven menu needs, focus and moving between widgets with a stick or d-pad, and leaves
the layout, the look and what each choice does to your game.

This guide follows LineSweeper's pause menu,
<RepoLink path="samples/linesweeper/states/pause_state.cpp">`states/pause_state.cpp`</RepoLink>:
four rows, *Resume*, *Restart*, *Colours* and *Quit*, over the dimmed game.

## The widgets

Widgets are game objects, so they go in a scene like anything else. The engine's set is small:

| Widget | What it is |
| --- | --- |
| `UiText` | A line of text. |
| `UiTexture` | A frame from a sprite sheet, in a rectangle. |
| `UiContainer` | A widget holding other widgets, so a compound row can be one thing. |

Each takes a name first, which is how a container finds a child. The set is small because it is
open: a widget is a class you can derive from, and a game's own widgets (a slider, a row with a
label and a value) are classes the game writes. It need not write those two from scratch:
<RepoLink path="samples/components">`samples/components`</RepoLink> has an option row and a
slider, each a header, a source file and its tests, to copy into your game and edit, and the
Examples page's [Components](/examples/#components-the-pieces-you-copy) section shows them.

**There is no layout engine.** You position widgets yourself. The pause menu measures each row's
text and centres it, as the [Sprites and text guide](/docs/guides/sprites-and-text/#text) shows.

## The focus group

A `FocusGroup` holds the widgets the cursor can land on, each with the action that runs when it is
chosen. The pause menu lists its four rows with the answer each would give; the *Colours* row's is
never given, because its action does not close the menu:

<SourceFile path="samples/linesweeper/states/pause_state.cpp" from="const std::array<Row, 4> rows = { {" to="} };" />

then adds them. Three actions pop the menu with their answer; the *Colours* row's action changes
the palette, rewrites its own text and leaves the menu open:

<SourceFile path="samples/linesweeper/states/pause_state.cpp" from="for (std::size_t index = 0; index < rows.size(); ++index)" to="}" />

Popping from inside an action is safe: the action runs inside the menu's `update()`, and the stack
waits for that to return before it destroys the menu.

The group colours its widgets to show focus: white for the focused one, grey for the rest, dim
grey for one that is disabled, darker than an enabled unfocused row. Pass a `FocusStyle` to the
constructor for other colours, and call `set_enabled(widget, false)` to grey out a choice that is
not available.

## Moving and choosing

Each step the menu turns input into a direction, moves the focus, and activates on confirm:

<SourceFile path="samples/linesweeper/states/pause_state.cpp" from="void PauseState::update(float dt)" to="}" />

`move(slot, direction)` finds the **nearest widget in that direction** by looking at where the
widgets are on screen, not at the order they were added. A grid of buttons, a column and a row
all navigate correctly with no extra code, and by default moving off one edge wraps to the other.
`move` returns whether the focus actually moved, which is when a menu would play a cursor sound.

`activate(slot)` runs the focused widget's action, and reports whether it ran, or was refused
because the widget is disabled.

The rows are one column, so the pause menu gives only up and down to `move`: in one column, a
sideways `move` could only wrap the cursor to a row the player did not point at. Left and right
instead step the palette while the cursor is on *Colours*, and do nothing elsewhere.

Directions come from [`DirectionRepeat`](/docs/guides/input/#directions-for-menus), which turns a
held stick or key into one move at once and then repeated moves, the way menus in console games
behave. The pause menu handles cancel first, so the button that opened the menu always closes it,
whatever the cursor is on.

selection, and the menu writes it in place.

## Drawing over the game

The pause menu says `covers_screen()` is false, so the match keeps drawing underneath it, and its
first object is a full-screen rectangle of translucent black that dims the match. Its scene is
drawn after the match's, so it draws on top. See
[Drawing over the world](/docs/concepts/drawing/#drawing-over-the-world).

## Split-screen menus

`FocusGroup` takes a number of **slots**, one per player, and every call names the slot it is
for. Each player has their own cursor in the same group, which is what a character-select screen
needs. The pause menu is single-player and uses slot 0 throughout.

The <RepoLink path="samples/local_multiplayer/join_state.cpp">local-multiplayer join screen</RepoLink>
is a copyable two-player example. Each keyboard half or pad slot joins one player, then each
player moves and selects READY or LEAVE independently. Its group and repeat clocks are separate:

<SourceFile path="samples/local_multiplayer/join_state.h" from="labrador::FocusGroup focus_;" to="std::array<labrador::DirectionRepeat, Arena::player_count> repeats_;" />

The screen uses `just_connected` and `just_disconnected` to explain pad changes and remove an
observed disconnected assignment. Joining consumes that press; it cannot also select READY.
The sample's <RepoLink path="samples/local_multiplayer/join_rules.cpp">value-based rules</RepoLink>
keep player binding and readiness outside the engine. [Local multiplayer](/docs/guides/local-multiplayer/)
explains the source-to-player mapping, controls and identity limits.

## Accessibility

Labrador provides [keyboard, controller, mouse and touch input](/docs/guides/input/), UI focus
and directional navigation. The default focus style distinguishes rows by brightness, and your
game can supply its own colours. In the browser, Tab remains available to move focus away from
the canvas. The drawn widgets and game state are not exposed to screen readers by the engine.

Your game owns layout, styling, contrast, accessibility options, and its actions and bindings,
including any rebinding. Labrador has no engine action map; games can implement remappable
controls through their own [binding tables](/docs/guides/input/#binding-tables).

LineSweeper aims for keyboard and controller play, clear focus, readable contrast,
reduced-motion options and selectable colour-vision-deficiency palettes. Its documentation
states what has been verified and any remaining limitations. The sample owns these choices;
other games decide their own accessibility aims.

Physical controller play still awaits the
<RepoLink path="docs/port/web-to-be-tested.md" hash="needs-a-gamepad-m4">recorded hardware checks</RepoLink>.
LineSweeper's landing shadow meets 3:1 against the empty well for every piece, checked by a test.
In a browser whose system asks for reduced motion, LineSweeper throws an eighth of the sparks
from each line clear, landing and top-out; the desktop build does not ask.
The pause menu's *Colours* row selects a piece palette for **Protanomaly / Protanopia**,
**Deuteranomaly / Deuteranopia** or **Tritanomaly / Tritanopia**, beside the standard one. The
palettes were chosen by simulation and checked against the landing-shadow contrast and the flash
criteria; no player with a colour-vision deficiency has validated them yet, and the selection is
not saved. The sample's
<RepoLink path="samples/linesweeper/README.md" hash="colour-vision-palettes">README</RepoLink>
records the colours, the method and their limits.
