A project started from [Start your own project](/docs/get-started/your-project/) is tested from
its first commit. It has two tests, and ctest runs them:

```bat
ctest --preset x64-debug
```

`MyGameTests` runs the game's rules with no window, no graphics device and no input device.
`MyGameSmokeTests` starts the game itself, hidden, lets it draw a few frames and quits. The first
says the game's arithmetic is right; the second says the game still starts, which is what an
engine upgrade or a moved content file breaks first. Neither is a test framework of Labrador's:
the first is doctest, the second is a switch in your `main.cpp`, and both are yours to change.

## Rules in a library of their own

A rule that asks the platform a question cannot be tested without one. The template's way round
that is to keep everything the game decides in `game\rules`, taking what the devices said as plain
values, and to let the states do the talking to the engine. `HelloState` reads the stick and the
keys, hands them to the rules as directions, and places its label where the rules say:

<SourceFile path="samples/minimal/states/hello_state.cpp" from="this->motion_ = step_motion(this->motion_," to="keyboard_direction(keyboard), dt);" />

The rules are ordinary functions on ordinary values:

<SourceFile path="samples/minimal/rules/motion.h" from="struct Motion" to="labrador::Vector2F greeting_position(const Motion& motion);" />

**The wall is the build file, not a convention.** The rules are a static library that links
`LabradorMath`, the engine's maths on its own, and the compiler settings, and nothing else of the
engine. A call from `game\rules` into the engine's compiled code, a window or a renderer, fails
to link, so the rules cannot start depending on a device without the build saying so. The wall
catches calls rather than includes: an engine header still compiles there, and what is inline or
constant in it links. The test
target links the rules and doctest:

<SourceFile path="website/src/walkthrough/game-CMakeLists.txt" from="add_library(MyGameRules STATIC" to="add_test(NAME MyGameTests COMMAND MyGameTests)" />

and a test is a doctest case that calls the rules and checks what came back:

<SourceFile path="samples/minimal/tests/motion_tests.cpp" from={'TEST_CASE("a step moves the centre and turns the greeting")'} to="}" />

The cases read `move_speed` and `orbit_radius` rather than repeating their values, so retuning the
game does not break them; changing what a step *does* does.

### Adding tests

- **A new rule** goes in `game\rules`, and its `.cpp` is listed in `MyGameRules`. A rule that
  needs the time, a random number or the input is handed them as arguments, the way
  `step_motion` is handed `dt` and two directions.
- **A new test file** goes in `game\tests` and is listed in `MyGameTests`. One target holds all
  of them and is one ctest entry; doctest prints how many cases ran.
- **doctest comes from vcpkg.** Your `vcpkg.json` names it beside the engine's dependencies, and
  `find_package(doctest CONFIG REQUIRED)` finds it. A project made from an older version of the
  page, whose manifest has no `doctest`, adds `"doctest"` to its `dependencies` and configures
  again.

### A whole game tested this way

LineSweeper, the falling-block sample, is the same wall around a complete game. Its rules are
<RepoLink path="samples/linesweeper/rules">a library</RepoLink> that links nothing but the compiler
settings, and
<RepoLink path="tests/linesweeper/CMakeLists.txt">its tests</RepoLink> play scripted games of four
thousand ticks and compare the result byte for byte, with no window and no device. Its input
reaches the rules as one byte per step, read from a binding table by the play state, which is
the same split as the template's: the state reads the devices, the rules see values. Its
<RepoLink path="samples/linesweeper/README.md">README</RepoLink> records
why it is arranged that way.

## Inspect draws with the null backend

Use a second configure with `LABRADOR_RENDER_BACKEND=null` and
`LABRADOR_AUDIO_BACKEND=null` for tests that inspect draw requests. Backend
selection happens at configure time; keep the regular build for playing and
give the recording build its own directory.

In the consumer `CMakePresets.json` from the walkthrough, add this object to
`configurePresets`. It inherits the existing Debug toolchain/settings, and
the base's `${presetName}` binary directory gives it a separate build tree:

```json
{
  "name": "x64-debug-null",
  "inherits": "x64-debug",
  "cacheVariables": {
    "LABRADOR_RENDER_BACKEND": "null",
    "LABRADOR_AUDIO_BACKEND": "null"
  }
}
```

Add the matching objects to `buildPresets` and `testPresets`, respectively:

```json
{ "name": "x64-debug-null", "configurePreset": "x64-debug-null" }
```

```json
{
  "name": "x64-debug-null",
  "configurePreset": "x64-debug-null",
  "output": { "outputOnFailure": true }
}
```

The <RepoLink path="engine/render/null/recording.h">recording inspector</RepoLink>
is a **backend-internal, test-only interface**, not a published portable render
API. A consumer's null-only tests and benchmarks may include it at their engine
pin; review that source when moving the pin. This grants no exception to the
engine's backend include wall.

It exposes submitted sprites in view order, then call order: texture handles,
filter, viewport and four corners with position, UV and tint. Positions are in
view pixels, with the camera already applied; the viewport offset is separate.
Read after `submit()`. The renderer owns the returned vector and clears it at
the next `begin_frame()`, so copy entries needed across frames or its lifetime.

Put this complete example in `game/tests/draw_tests.cpp`. It creates no window,
Application, graphics API device or audio endpoint. Its texture is supplied
from memory and the null renderer records the draws. In your game, call your view's `draw` with these
DrawLists and check the texture, order or geometry your presentation should
produce:

```cpp
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include <doctest/doctest.h>

#include "engine/math/rectanglef.h"
#include "engine/math/rectanglei.h"
#include "engine/math/vector2f.h"
#include "engine/render/colour.h"
#include "engine/render/null/recording.h"
#include "engine/render/render_resources.h"
#include "engine/render/renderer.h"
#include "engine/render/resource_factory.h"
#include "engine/render/texture_data.h"
#include "engine/render/viewport.h"

#include <vector>

using namespace labrador;

TEST_CASE("drawing preserves view order, call order and sprite state")
{
    RenderResources resources; // Outlives the renderer that borrows it.
    Renderer renderer;
    renderer.create_device(nullptr, 640, 480, 2);
    renderer.set_resources(&resources);

    TextureData texel;
    texel.width = 1;
    texel.height = 1;
    texel.levels.push_back(texture_level(texel.format, 1, 1, 0));
    texel.pixels.assign(4, 255);
    add_texture_asset(renderer, resources, "test:white", texel);
    const TextureHandle texture = resources.resolve_texture("test:white");
    const RectangleI source(0, 0, 1, 1);

    renderer.begin_frame();
    renderer.set_view_count(2);
    DrawList first = renderer.view(0);
    DrawList second = renderer.view(1);
    const Viewport right(320.0f, 0.0f, 320.0f, 480.0f);
    second.set_viewport(right);

    // Fill view 1 first: submit still emits view 0 before view 1.
    second.draw_sprite(texture, source, RectangleF(1.0f, 2.0f, 4.0f, 6.0f),
        Colour::white, 0.0f, Vector2F::zero, SpriteFlip::none, 0.0f);
    first.draw_sprite(texture, source, RectangleF(10.0f, 20.0f, 8.0f, 4.0f),
        Colour::white, 0.0f, Vector2F::zero, SpriteFlip::none, 0.0f);
    first.set_filter(TextureFilter::linear);
    first.draw_sprite(texture, source, RectangleF(30.0f, 40.0f, 3.0f, 5.0f),
        Colour::white, 0.0f, Vector2F::zero, SpriteFlip::none, 0.0f);
    renderer.submit();

    // The recorder returns a reference; retain a copy for later frames.
    const std::vector<RecordedSprite> drawn = recorded_sprites(renderer);
    renderer.end_frame();
    renderer.begin_frame();
    CHECK(recorded_sprites(renderer).empty());
    REQUIRE(drawn.size() == 3);
    CHECK(drawn[0].view == 0);
    CHECK(drawn[1].view == 0);
    CHECK(drawn[2].view == 1);
    for (const RecordedSprite& sprite : drawn)
    {
        CHECK(sprite.texture == texture);
    }
    CHECK(drawn[0].filter == TextureFilter::point);
    CHECK(drawn[1].filter == TextureFilter::linear);
    CHECK(drawn[2].filter == TextureFilter::point);
    CHECK(drawn[0].viewport == Viewport(0.0f, 0.0f, 640.0f, 480.0f));
    CHECK(drawn[2].viewport == right);
    CHECK(drawn[0].corners[0].position == Vector2F(10.0f, 20.0f));
    CHECK(drawn[0].corners[1].position == Vector2F(18.0f, 20.0f));
    CHECK(drawn[0].corners[2].position == Vector2F(10.0f, 24.0f));
    CHECK(drawn[0].corners[3].position == Vector2F(18.0f, 24.0f));
    CHECK(drawn[0].corners[0].texcoord == Vector2F::zero);
    CHECK(drawn[0].corners[3].texcoord == Vector2F(1.0f, 1.0f));
    CHECK(drawn[1].corners[0].position == Vector2F(30.0f, 40.0f));
    // Corners are view-local; the viewport offset is recorded separately.
    CHECK(drawn[2].corners[0].position == Vector2F(1.0f, 2.0f));
}
```

Add a separate target to `game/CMakeLists.txt`, where doctest is already found:

```cmake
if(LABRADOR_RENDER_BACKEND STREQUAL "null")
    add_executable(MyGameDrawTests tests/draw_tests.cpp)
    target_link_libraries(MyGameDrawTests PRIVATE
        LabradorEngine doctest::doctest labrador_settings)
    target_include_directories(MyGameDrawTests PRIVATE "${CMAKE_CURRENT_SOURCE_DIR}/..")
    add_test(NAME MyGameDrawTests COMMAND MyGameDrawTests)
endif()
```

The guard keeps this inspector-specific source out of other render builds.
List the view sources under test in this target too, or link your presentation
library. The project-root include path admits the walkthrough's `game/...`
headers. The existing rules target still links only maths. Configure, build and run
the draw test from your project root in the Native Tools prompt:

```bat
cmake --preset x64-debug-null
cmake --build --preset x64-debug-null --target MyGameDrawTests
ctest --preset x64-debug-null -R "^MyGameDrawTests$" --output-on-failure
```

Recordings prove the submitted commands and geometry. Pixel tests cover actual
rasterization; this backend produces no pixels and `read_back_buffer` throws
`std::logic_error`.

## The start-up check

`MyGame.exe --smoke-test` runs your first state in a hidden window, with the real window, device,
content and frame loop, and quits once 30 frames have been drawn, about half a second. It exits
0 when it got that far and 1 when anything threw, with the reason written to the standard error
stream instead of a message box, because nobody is there to close one. The build registers it:

<SourceFile path="website/src/walkthrough/game-CMakeLists.txt" from="add_test(NAME MyGameSmokeTests" to="set_tests_properties(MyGameSmokeTests" />

The timeout is for a loop that never draws. A missing content file fails it with the file
named, as the game would on your next launch:

```text
startup failure: No file at C:\dev\mygame\out\build\x64-debug\game\.\./fonts/jetbrains_mono_bold_16.spritefont.
```

`main.cpp` does it by wrapping the first state rather than by adding a flag to it, so
`HelloState` has no test code in it, and when your first state is a title screen of your own,
it is wrapped the same way:

<SourceFile path="samples/minimal/main.cpp" from="std::unique_ptr<State> first_state" to="return app.run(std::move(first_state));" />

**The regular render build needs a graphics device.** Debug Direct3D permits
Windows' WARP software fallback; Release has no WARP fallback. A preset for
OpenGL or Vulkan needs a driver. On a machine without the required device,
`ctest --preset <name> -E SmokeTests` runs the rest. The null configure above
instead checks startup with its recording renderer.

It presses no keys, so it checks that the game starts, not that it plays. The
separate draw test above inspects requests without proving device output.

## Drive the game with injected keys

To get past a title screen in a smoke run after moving your pin, inject keys into the running
game. **The engine reads the keyboard once per frame**, before your state's update: each key
event the window receives is held until that poll, which makes it visible to `held()` and,
for one frame, `pressed()`. A key pressed and released between two polls is never seen, so a
tap sent faster than a frame does nothing. Hold the key across at least one poll and release
it in a later one; at 60 frames a second, a hold of 100 ms spans several polls.

<SourceFile path="engine/input/keyboard.h" from="// For the shell or an input fixture." to="void on_key_up(Key key);" />

Two more things decide whether a key arrives. Injected keys go to the foreground window only,
so bring the game forward first. And losing focus releases every held key, so a key held while
another window takes focus is released at the next poll.

This script starts a game, brings its window forward, holds one key and saves the window
before and after. It sends set-1 scan codes through `SendInput`, which is how the Windows
window reads keys, so it presses the same physical key whatever the keyboard layout:

<SourceFile path="tools/input_drive/hold_key.ps1" collapsed />

Run against the Release minimal sample, holding the right arrow for half a second moves its
greeting about 200 pixels, its speed of 400 pixels a second for 0.5 seconds:

```bat
powershell -ExecutionPolicy Bypass -File tools\input_drive\hold_key.ps1 -Exe out\build\x64-release\samples\minimal\MinimalSample.exe -Key Right
```
