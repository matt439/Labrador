Everything Labrador draws is a textured rectangle: a sprite. Text is sprites cut from a font's
glyph atlas, and a solid rectangle is a sprite from a texture one pixel across. This guide covers
the files, the classes that draw them, and the colours.

## The files

| Kind | File | Made with |
| --- | --- | --- |
| Texture | `.dds` | Any tool that writes DDS, such as `texconv` from Microsoft's DirectXTex (below). |
| Font | `.spritefont` | `MakeSpriteFont` from Microsoft's DirectX Tool Kit, which renders an installed font into an atlas (below). |
| Sprite sheet | `.dds` and `.json` with the same name | A texture, plus a JSON file naming rectangles in it (below). |

A texture can be uncompressed 32-bit colour (`R8G8B8A8` or `B8G8R8A8`), 16-bit `B4G4R4A4`, or
block-compressed BC1, BC2 or BC3. Anything else is refused at load, with the file named. Each
file is listed in the [manifest](/docs/concepts/resources/#the-manifest) by name, without its
extension.

## Making textures and fonts

Both tools are free Windows programs from Microsoft, each a single executable attached to its
project's releases. Neither is needed to build or run the samples, and neither is a dependency of
the engine. The commands below were checked with the `may2026` release of each.

- [`texconv`](https://github.com/microsoft/DirectXTex/wiki/Texconv): `texconv.exe` from the
  [DirectXTex releases](https://github.com/microsoft/DirectXTex/releases).
- [`MakeSpriteFont`](https://github.com/microsoft/DirectXTK/wiki/MakeSpriteFont):
  `MakeSpriteFont.exe` from the [DirectX Tool Kit releases](https://github.com/microsoft/DirectXTK/releases).

**A texture from a PNG**, run from your game's folder:

```bat
texconv -f R8G8B8A8_UNORM -m 1 -pmalpha -y -o content\textures hero.png
```

This writes `content\textures\hero.dds`, and the folder must already exist. The `-f` is required:
without it texconv keeps the PNG's sRGB format, which only the DX10 extended header can describe,
and the engine refuses that header at load. `-m 1` writes one level rather than a mip chain.
`-pmalpha` multiplies each colour by its alpha, which is what the engine's blending expects
([Colours and blending](#colours-and-blending), below). `-y` overwrites an existing file.

**A font from an installed font:**

```bat
MakeSpriteFont "JetBrains Mono" content\fonts\jetbrains_mono_bold_16.spritefont /FontSize:16 /FontStyle:Bold
```

The first argument is the family name of a font installed on the machine; a path to a font file
is not accepted. With no `/CharacterRegion` the atlas holds the 95 printable ASCII characters,
U+0020 to U+007E. The tool premultiplies the alpha itself and writes a BC2 atlas, which the engine
reads as it is. The template's own atlas was built at these settings from the Bold face of
JetBrains Mono 2.304, and the
<RepoLink path="samples/minimal/README.md">minimal sample's README</RepoLink> records the font's
and the atlas's checksums, so a rebuild can be compared byte for byte.

Then list the new file in `content\manifest.json`. On Windows a folder of content is copied beside
the executable by a line in your `CMakeLists.txt`, and a new folder such as `textures` needs a line
of its own ([Assets](/docs/guides/assets/)).

### The template's font and its licence

The template's only font, `content/fonts/jetbrains_mono_bold_16.spritefont`, is an atlas rendered
from JetBrains Mono Bold, which is licensed under the SIL Open Font License 1.1. The licence is
`content/fonts/OFL.txt`, beside the atlas, and starts with the font's copyright line. You may ship
the atlas in your game, whether you sell the game or not, provided `OFL.txt` goes with every copy
of the atlas and the font is not sold on its own. The atlas stays under the OFL rather than your
game's licence. <RepoLink path="NOTICE">NOTICE</RepoLink> records it with the repository's other
third-party terms. Every sample draws its text from the same atlas.

To use a different font, install it and run the `MakeSpriteFont` command above with its name.
Then change the atlas's name in `content/manifest.json`, in the `font_name` constant at the top of
`states/hello_state.cpp` and `states/confirm_state.cpp`, and in the `.spritefont` path the browser
build lists in `CMakeLists.txt`. Delete the JetBrains Mono atlas and its `OFL.txt`, and put the
new font's licence beside its atlas if the licence asks to travel with it.

## Text

There are three text classes, for three places text appears:

| Class | Is a | Use it for |
| --- | --- | --- |
| `Label` | `GameObject` | Text in a scene: added once, culled and drawn with everything else. |
| `Text` | a drawable you draw yourself | Text a state draws directly, without a scene. |
| `UiText` | a widget | A row in a menu that can take focus ([Menus](/docs/guides/menus/)). |

All three take the same core arguments: the text as a **wide string**, the font's name from the
manifest, a position, and the render resources the font is resolved against. The minimal sample's
greeting is a `Label`:

<SourceFile
	path="samples/minimal/states/hello_state.cpp"
	from="this->greeting_ = this->scene_->add(std::make_unique<Label>("
	to="labrador::Colour::white));"
/>

The font name is resolved to a handle in the constructor, so a misspelt name throws there, and
the text is measured once whenever it changes rather than on every frame. `set_text`,
`set_position`, `set_colour` and `set_scale` change it afterwards, from `update()`.

**Text is wide** (`std::wstring`, written `L"..."`) all the way to the renderer, so drawing it
never converts or allocates. A font can only draw the characters it was made with. Before showing
text that came from outside the game, such as a player's name, check it with
`RenderResources::can_render(font, text)`.

**Centring text means measuring it.** `RenderResources::measure_text(font, text)` returns its
size. LineSweeper's pause menu centres each row this way, once, when the menu is built:

<SourceFile path="samples/linesweeper/states/pause_state.cpp" from="const auto centred = [&]" to="};" />

The position is rounded down to a whole pixel. Half of an odd width is half a pixel, and text
there sits with every pixel centre on the edge between two texels of its font. Each graphics
backend picks between them its own way, and can tear a glyph doing it. Any other fraction draws
as it would on the nearest whole pixel, under the point filter.

The engine has no layout system: positions are numbers your game works out, as here.

### Which languages the text path can draw

Text is drawn one glyph per code unit, left to right, with each glyph's own advance. There is no
kerning, no shaping or ligatures, no right-to-left or bidirectional ordering, and no combining
mark placed over the letter before it: a mark is a glyph of its own that moves the pen. The only
line break is `\n`.

So a script in which every character is one precomposed glyph is in reach, given a font made with
those characters:

| In reach | Out of reach |
| --- | --- |
| Latin with precomposed accents (`é`, not `e` plus a combining accent) | Arabic and Hebrew, which are right-to-left and joined |
| Greek and Cyrillic | Devanagari and the other Indic scripts, and Thai, which need shaping and placed marks |
| Chinese, Japanese kana and kanji, and Korean Hangul syllables | Emoji and anything else outside the Basic Multilingual Plane |

No font in this repository holds anything but printable ASCII, so none of these scripts has been
drawn here; a large character set is also a large atlas, which is your game's to size.

A character beyond the Basic Multilingual Plane (above U+FFFF) is not supported. A narrow string
converted with `widen()` holds it as two UTF-16 code units, which draw as two stand-in glyphs on
every platform. A wide literal in your source does not agree across platforms: `wchar_t` is 16
bits on Windows and 32 in the browser build, so the same `L"..."` is two units and two stand-ins
on Windows but one unit and one stand-in in the browser. `can_render` reports either as text the
font cannot draw.

## Sprites from a sheet

A sprite sheet is one texture with named rectangles in it. Its JSON file lists **frames**, each a
named rectangle, and **animation strips**, each a run of equal-sized frames laid out left to right
from a first frame:

```json
{
    "sprite_frames": [
        { "name": "coin", "position": { "x": 0, "y": 0 }, "size": { "w": 16, "h": 16 } },
        { "name": "hero_idle", "position": { "x": 0, "y": 16 }, "size": { "w": 16, "h": 32 },
          "origin": { "x": 8, "y": 32 } }
    ],
    "animation_strips": [
        { "name": "hero_walk", "first_frame": { "x": 16, "y": 16, "w": 16, "h": 32 },
          "frame_count": 6, "frame_time": 0.1, "looping": true }
    ]
}
```

`origin` is optional, in texels from the frame's top-left; it is the point a sprite is placed and
rotated by, such as the middle of a character's feet. A sheet whose packer rotated frames to fit
them is refused, because the engine draws frames as they are stored. Every key is checked when the
sheet loads, and a missing or mistyped one names the file and the key.

`TextureObject` draws one named frame from a sheet, and is designed to be **inherited alongside
`GameObject`**, so your own class gets its drawing and keeps its own update. Its constructor
takes the sheet name and the frame name. It has `draw(draw_list, destination_rectangle)` and
`draw(draw_list, position, scale)`, and a `draw_with` that takes the colour or flip as a
parameter instead.

The engine has no animation player. To play a strip, resolve it with
`SpriteSheet::resolve_animation_strip`, keep the elapsed time in your own `update()`, and pass
`AnimationStrip::calculate_frame(index)` to the `SpriteSheet::draw` overloads that take a source
rectangle. Because several views can draw
the same object at once, a tint or flip that varies from draw to draw is passed through
`draw_with` rather than set on the object first. None of the six samples uses a sprite sheet
yet; the engine's tests do.

## Solid rectangles

There is no rectangle-drawing call, because a solid rectangle is a sprite from a texture one
white pixel across, stretched and tinted. The engine puts that texture in every game's table, so
no content file is needed: resolve it by `white_texture_name`, from
`engine/render/resource_factory.h`, as the collision sample does:

<SourceFile
	path="samples/collision/collision_state.cpp"
	from="void CollisionState::init()"
	to="this->refresh_view();"
/>

The application shell adds it when it sets up the table and again after a device restore. Code
that builds its own `Renderer` and `RenderResources`, such as a test, calls
`add_white_texture(renderer, resources)` itself. LineSweeper ships its own white texel instead,
and every block, panel and line on its screen is that pixel stretched and tinted. This is the
darkening layer its pause menu draws over the game:

<SourceFile path="samples/linesweeper/states/pause_state.cpp" from="void draw(DrawList& draw_list) const override" to="}" />

`draw_sprite` takes a source rectangle in texels, here the one pixel, and a destination rectangle
in world space, here the whole screen.

## Colours and blending

`Colour` holds four floats from 0 to 1, and can be built from floats, from bytes
(`Colour(240, 152, 0)`), or from a hex string. It has the usual named colours:
`Colour::white`, `Colour::goldenrod`, `Colour::dark_gray` and so on.

**Blending is premultiplied.** A drawn pixel lands as `source + destination × (1 − source alpha)`.
For an ordinary translucent colour, multiply the colour by its alpha as well, which is what
LineSweeper's `faded` does:

<SourceFile path="samples/linesweeper/presentation/palette.h" from="constexpr labrador::Colour faded(" to="}" />

The same rule gives additive light for free. With alpha at zero the destination is untouched and
the colour is simply added, so overlapping draws brighten towards white. That is LineSweeper's
`glowing`, and its whole particle effect:

<SourceFile path="samples/linesweeper/presentation/palette.h" from="constexpr labrador::Colour glowing(" to="}" />

**A texture must arrive premultiplied, because the engine does no premultiplication at load.**
A `.dds` file's texels are drawn as they are stored, so a soft-edged sprite is premultiplied when
it is converted, which is what texconv's `-pmalpha` does
([Making textures and fonts](#making-textures-and-fonts), above). A texture converted without it
keeps the full colour in its half-transparent edge texels and adds that colour to whatever is
behind, which shows as a light fringe or halo round the sprite, and a fully transparent area whose
colour is not black shows as a coloured box. Premultiplying a texture twice, by passing `-pmalpha`
to a source that was already premultiplied, darkens its edges instead. MakeSpriteFont's atlases
are premultiplied by the tool.

## Filtering

`DrawList::set_filter` chooses between smooth (linear) and blocky (point) sampling when a texture
is scaled, for every draw after it in that view. Pixel art usually wants point sampling. Changing
the filter partway through a view is allowed and costs a little, so group draws by filter.
