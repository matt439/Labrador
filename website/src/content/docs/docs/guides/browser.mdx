The game you started in [Start your own project](/docs/get-started/your-project/) builds for a
browser as well as for Windows. The same states, rules and content are compiled to WebAssembly by
Emscripten, the renderer draws through WebGL2, and the result is a web page. Nothing in your game's
code changes: the browser build uses a second entry point, `main_web.cpp`, and a page,
`web/shell.html`, both of which came with your copy of the minimal sample.

This page adds the browser build to that project. You need the project as Get Started leaves it,
and one more install.

## Install Emscripten

Labrador's browser build is built and tested with **Emscripten {EMSDK_VERSION}**, the version its
CI pins. Install that version rather than the latest: the engine compiles with warnings as errors,
and a newer compiler can warn about something the pinned one does not. Emscripten is installed
with its own installer, `emsdk`, which needs Git and, the first time it runs, Python 3 on your
`PATH`. Neither Visual Studio nor Git brings Python, and on a new Windows 11 machine `python` is a
stub that offers the Microsoft Store rather than running anything, so check it first:

```bat
python --version
```

If that does not print `Python 3` and a version, install Python from
[python.org](https://www.python.org/downloads/windows/) or with
`winget install Python.Python.3.13`, open a new prompt and check again. Then, in the x64 Native
Tools Command Prompt:

<Code
	lang="bat"
	code={`cd C:\\dev
git clone https://github.com/emscripten-core/emsdk.git
cd emsdk
emsdk install ${EMSDK_VERSION}
emsdk activate ${EMSDK_VERSION}`}
/>

`emsdk install` downloads the compiler, and the Node and Python it runs on, into `C:\dev\emsdk`.
From then on `emsdk` runs on its own Python rather than yours. Nothing is installed anywhere else,
and deleting the folder uninstalls it.

### Set EMSDK in your build prompt

The browser build needs two environments at once. The x64 Native Tools Command Prompt puts CMake
and Ninja on your `PATH` and sets `VCPKG_ROOT`, which the browser build still uses, and
Emscripten's `emsdk_env.bat` sets `EMSDK` and puts `emcc` on your `PATH`. Open the Native Tools
prompt as before, then run Emscripten's script in it:

```bat
C:\dev\emsdk\emsdk_env.bat
```

Do this every time you open a prompt for a browser build. The settings last until you close the
prompt, and the Windows build is not affected by them. Check that it worked:

```bat
echo %EMSDK%
emcc --version
```

The first should print `C:/dev/emsdk`, and the second should name {EMSDK_VERSION}.

If you configure without `EMSDK` set, the preset cannot find Emscripten's toolchain file, and
configure stops with:

```text
include could not find requested file:
  /upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake
```

The path starts at `/upstream` because `EMSDK`, which should come before it, is empty. Run
`emsdk_env.bat` in that prompt, delete the build folder, and configure again.

## Add a browser preset

Add three configure presets to your `CMakePresets.json`: a hidden `wasm-base` and the two you
use, `wasm-debug` and `wasm-release`. Add a build preset and a test preset for each of the two,
as for the x64 ones. The project's
[CMakePresets.json](/docs/get-started/your-project/) on the Get Started page already has them;
these are its three wasm entries in the `configurePresets` array, as a fragment of it:

<SourceFile
	path="website/src/walkthrough/CMakePresets.json"
	from={'"name": "wasm-base",'}
	to={'"cacheVariables": { "CMAKE_BUILD_TYPE": "Release" }'}
/>

The toolchain is still vcpkg's, so vcpkg still installs the engine's dependencies.
`VCPKG_CHAINLOAD_TOOLCHAIN_FILE` tells vcpkg to hand over to Emscripten's toolchain after it, and
`VCPKG_TARGET_TRIPLET` builds those dependencies for WebAssembly instead of x64. The Windows-only
packages in your `vcpkg.json`, DirectXTK and XAudio2, are skipped for this triplet.

The preset does not name a renderer, an audio backend or an input backend. In a browser build
Labrador chooses the only ones that work there: the OpenGL renderer, which draws through WebGL2,
Web Audio, and the browser's Gamepad API. If a preset asks for a Direct3D or Vulkan renderer in a
browser build, configure stops and says that it must be `gl` or `null`.

## Build the game as a page

The `game/CMakeLists.txt` from Get Started already has the browser half of the build. It is the
`if(EMSCRIPTEN)` block, which a browser build reads in place of everything below it:

<SourceFile path="website/src/walkthrough/game-CMakeLists.txt" from="if(EMSCRIPTEN)" to="endif()" />

- **`main_web.cpp` replaces `main.cpp`.** It starts the same first state. In a browser
  `Application::run` does not return, and everything on the stack below it is destroyed before
  the first frame, so the `Application` is a `static` rather than a local variable. A failure is
  written to the browser's console and passed to the page, because a page has no message box.
- **`SUFFIX ".html"`** makes the build write `MyGame.html`, with `MyGame.js` and `MyGame.wasm`
  beside it.
- **`--embed-file`** packs everything in `game/content` into the module, at the paths the
  Windows build copies it to, so `load_manifest("./manifest.json")` finds the same files.
- **`--shell-file`** makes the page from `web/shell.html`. Emscripten puts the module's script
  where the page says `{{{ SCRIPT }}}`.
- **The rules' tests run under Node**, which Emscripten's toolchain gives ctest. The start-up
  check is not in this branch, because it needs a command line and a page has none.

Then configure, build and test it, in the prompt where you ran `emsdk_env.bat`:

```bat
cmake --preset wasm-debug
cmake --build --preset wasm-debug
ctest --preset wasm-debug
```

The first configure installs doctest again, built for WebAssembly; it is the only package the
browser build needs, so this is quick. ctest runs `MyGameTests` and reports `100% tests passed, 0 tests failed out of 1`. The page is
`out\build\wasm-debug\game\MyGame.html`.

## The page, and what it owes the module

`web/shell.html` is yours to change. Its title, its status line and its styles are the minimal
sample's, and you replace them with your own. Set `Module` before Emscripten's generated script
starts the game. The template supplies a canvas and two of the four optional page callbacks:

<SourceFile path="samples/minimal/web/shell.html" from="var Module = {" to="};" lang="js" />

**`Module.canvas` must be the actual canvas element**, present before the game starts. The page
owns its place in the DOM and its size in CSS; the engine follows that size and the device pixel
ratio when setting the drawing buffer. Keep `tabindex="0"` on the canvas so it can take keyboard
focus, and `touch-action: none` so a finger on it does not scroll the page. Call `canvas.focus()`
when the player starts playing, as the template does.

The four callbacks below are optional. **Names are exact and case sensitive.** A misspelled name
is silently ignored, with no warning; a value that is not a function is ignored too. The engine
reads each callback from `Module` when it is due.

| Callback | When it is called | What the page can show |
| --- | --- | --- |
| `Module.onQuit()` | The game calls `Application::quit()` (or closes its `Window`), after the frame loop has been cancelled and the window's input and page listeners have been removed. It has no arguments. | The game has ended; offer a reload or another game. |
| `Module.onError(message)` | The template's `main_web.cpp` forwards a startup exception, or the browser window catches an exception from a frame or input handler. `message` is a string, also written to the console. A caught frame or input failure stops the loop and window listeners before this call. | The reason the game could not start or continue. |
| `Module.onContextLost()` | The renderer observes a lost WebGL2 context, once per loss, at the next `begin_frame`. It has no arguments. | Graphics are unavailable and restoration is awaited. |
| `Module.onContextRestored()` | At `begin_frame`, after the renderer and the game's device resources have been rebuilt. It has no arguments; that frame can now draw again. | Remove the graphics-loss message. |

Keep the startup error forwarding in `main_web.cpp` when you change the entry point. A script,
fetch or WebAssembly compilation failure can happen before the engine runs, so the page must
handle loader failures separately; `onError` cannot report every failure to load the module.

The context callbacks run from a frame, rather than directly from the browser's context events.
Loss is reported before restoration, even if both happen between two frames. Restoration has no
deadline: if the browser never restores the context, `onContextRestored` never arrives and the
canvas stays blank. Keep the loss message visible until restoration or a new page load.

### Quit before removing the canvas

**Keep the same canvas attached while the game is running.** Removing it from the DOM does not
stop the frame loop, release the WebGL2 context or unregister the window's listeners. It leaves
a hidden running game. Changing `Module.canvas` is not a way to stop or move that game either.

Before replacing or removing the canvas, arrange for the game to call `Application::quit()` and
wait for `onQuit`. The template's Escape/Enter confirmation is one way to reach it. There is no
built-in JavaScript stop function; a host that needs a stop button must connect it to its own
game's quit path.

Quit cancels the loop and removes the window's listeners, but the static `Application` and its
WebGL2 context remain in that module instance. Reload the template's page to play again. An
ES-module host such as LineSweeper's creates a fresh module instance and a fresh canvas for each
game, then drops the old canvas after quit.

## Serve it and open it

A browser will not run a WebAssembly module opened from `file://`, so serve the folder over HTTP.
Emscripten came with a Python, which can do it:

```bat
"%EMSDK_PYTHON%" -m http.server 8000 --bind 127.0.0.1 --directory out\build\wasm-debug\game
```

Then open `http://127.0.0.1:8000/MyGame.html` in Chrome, Edge or Firefox. You should see the same
greeting as the Windows build, and the same keys work. Press Ctrl+C in the prompt to stop the
server.

For a page to put on a site, build `wasm-release` the same way. Its page is
`out\build\wasm-release\game\MyGame.html`, and the three files beside each other are all you
upload. [Put your game on a web host](/docs/guides/web-host/) says what the host must send with
them.

## What has and has not been checked

On 25 October 2026 this page was followed on Windows 11: Emscripten {EMSDK_VERSION} installed into
an empty folder by the commands above, on a machine that already had Python 3 on its `PATH`, and
the project from Get Started configured with it, built under both presets, its test run under Node, and its page served and loaded in headless Chrome,
which drew the greeting, took Escape and Enter, and quit with nothing in the console. Installing
Python first, on a machine or account without it, has not been followed. CI's `wasm-consumer` job builds that
project's `wasm-release` page and loads it the same way on every pull request to Labrador.

The browser build has been checked in desktop Chrome and, for LineSweeper's page, Firefox. It has
not been checked in Safari, on a phone, with a real touchscreen or with a physical gamepad.
[Platform support](/why/#platform-support) says where each of those stands; say the same on your
own page until you have checked them yourself.

The browser presets build into their own folders under `out\build`, so the Windows build and its
two tests are exactly as before. [Check your game in CI](/docs/guides/ci/) builds only the Windows
preset.
</Aside>
