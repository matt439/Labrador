The game you started from the [starter project](/docs/get-started/starter/) or
[Start your own project](/docs/get-started/your-project/) builds for a browser as well as for
Windows. The same states, rules and content are compiled to WebAssembly by **Emscripten**, the
renderer draws through WebGL2, and the result is a web page you open in Chrome, Edge or Firefox.
Nothing in your game's code changes: the browser build uses a second entry point,
`main_web.cpp`, and a page, `web/shell.html`, both of which came with your project.

This page installs Emscripten, builds the page, serves it from your own machine and opens it,
then changes the game and sees the change. The first time takes about 20 minutes, most of it
the download; you need about **2.2 GB** of free disk, and no Git. To then put the page on the
internet for a friend to play, [Put your game on the web](/docs/guides/your-web-page/)
continues from here.

You need the project as [Get the starter project](/docs/get-started/starter/) leaves it, in
`C:\dev\mygame`, and the x64 Native Tools Command Prompt from
[Install the tools](/docs/get-started/prerequisites/). Every command on this page runs in that
prompt, one box at a time.

## Install Emscripten

Labrador's browser build is built and tested with **Emscripten {EMSDK_VERSION}**, the version its
CI pins. Install that version rather than the latest: the engine compiles with warnings as errors,
and a newer compiler can warn about something the pinned one does not. Emscripten comes with its
own installer, `emsdk`, which needs Python the first time it runs and then brings its own.

<Steps>

1. **Check that Python runs.** In the x64 Native Tools Command Prompt:

   ```bat
   python --version
   ```

   If it prints `Python 3.10` or a later version, such as `Python 3.14.2`, go on to step 2.
   emsdk refuses an older Python, such as `Python 3.9.13`: install a new one as below. Otherwise
   it prints one of these:

   - `'python' is not recognized as an internal or external command, operable program or batch
     file.`: Python is not installed.
   - `Python was not found; run without arguments to install from the Microsoft Store, or disable
     this shortcut from Settings > Manage App Execution Aliases.`: Python is not installed, and
     `python` is Windows' shortcut to the Microsoft Store. Typing `python` alone opens the Store.

   Then install the **Python install manager**, which is what python.org now gives Windows: open
   [its page in the Microsoft Store](https://apps.microsoft.com/detail/9NQ7512CXL7T) and click
   **Install**, or run this in the prompt:

   ```bat
   winget install 9NQ7512CXL7T -e --accept-package-agreements --accept-source-agreements --disable-interactivity
   ```

   Close the prompt, open a new x64 Native Tools Command Prompt, and run `python --version`
   again. With the install manager and no Python yet, Python's documentation says the first
   `python` downloads and installs the latest Python before it answers, so it can take a while. If `python` still opens the
   Store, open **Start**, type `Manage app execution aliases`, open it, and turn the **Python
   (default)** entries off and on again, as Python's documentation says. Python's
   [Using Python on Windows](https://docs.python.org/3/using/windows.html) has the other ways to
   install it.

2. **Download emsdk.** It is a ZIP of about 210 KB from GitHub, and Windows' own `curl` and
   `tar` fetch and extract it, so you do not need Git or a browser:

   <Code
   	lang="bat"
   	code={`if not exist C:\\dev mkdir C:\\dev
   cd /d C:\\dev
   curl.exe --fail --location --output emsdk.zip https://github.com/emscripten-core/emsdk/archive/refs/tags/${EMSDK_VERSION}.zip
   tar -xf emsdk.zip
   ren emsdk-${EMSDK_VERSION} emsdk
   del emsdk.zip
   dir /b emsdk\\emsdk.bat`}
   />

   `curl` shows a small table of progress and is done in a second; `tar`, `ren` and `del` print
   nothing when they work. The ZIP holds one folder, `emsdk-` and the version, which `ren`
   renames to `C:\dev\emsdk`. The last line checks it, and prints:

   ```text title="Output"
   emsdk.bat
   ```

   <Aside title="If you use Git">
   `git clone https://github.com/emscripten-core/emsdk.git` in `C:\dev` makes the same
   `C:\dev\emsdk` folder, about 4 MB, in two seconds. Emscripten's own instructions use it, and
   say the ZIP works as well; the steps below are the same either way.
   </Aside>

   />

the one from step 1. To uninstall Emscripten, delete the folder: `rmdir /s /q C:\dev\emsdk`.

### Set EMSDK in your build prompt

The browser build needs two set-ups in one prompt. The x64 Native Tools Command Prompt puts
CMake and Ninja on your `PATH` and sets `VCPKG_ROOT`, which the browser build still uses;
Emscripten's `emsdk_env.bat` sets `EMSDK` and puts its compiler, `emcc`, on your `PATH`. Open the
Native Tools prompt as always, then run Emscripten's script in it, and go to your project:

```bat
C:\dev\emsdk\emsdk_env.bat
cd /d C:\dev\mygame
```

**Do this in every new prompt you use for a browser build.** The settings last until you close
the prompt, and do not change the Windows build. The script prints a screenful, which is normal;
the `PATH =` line is very long, and is shortened here:

```text title="Output"

Adding directories to PATH:
PATH += C:\dev\emsdk
PATH += C:\dev\emsdk\upstream\emscripten

Setting environment variables:

```

Run in the same prompt a second time, it prints only three lines: the first, `Setting environment
variables:` and the last. It prints the same three lines the first time if you run it in the

## Build the game as a page

Your `CMakePresets.json` already has two browser presets, `wasm-debug` and `wasm-release`, with
a build and a test preset for each. They are its three `wasm` entries in the `configurePresets`
array:

<SourceFile
	path="website/src/walkthrough/CMakePresets.json"
	from={'"name": "wasm-base",'}
	to={'"cacheVariables": { "CMAKE_BUILD_TYPE": "Release" }'}
/>

The toolchain is still vcpkg's, so vcpkg still installs the game's libraries.
`VCPKG_CHAINLOAD_TOOLCHAIN_FILE` tells vcpkg to hand over to Emscripten's toolchain after it, and
`VCPKG_TARGET_TRIPLET` builds those libraries for WebAssembly instead of x64. The Windows-only
packages in your `vcpkg.json`, DirectXTK and XAudio2, are skipped for this triplet. In a browser
build Labrador chooses the only renderer, audio and input that work there: OpenGL drawing through
WebGL2, Web Audio, and the browser's Gamepad API.

`game/CMakeLists.txt` has the browser half of the build too. It is the `if(EMSCRIPTEN)` block,
which a browser build reads in place of everything below it:

<SourceFile path="website/src/walkthrough/game-CMakeLists.txt" from="if(EMSCRIPTEN)" to="endif()" />

- **`main_web.cpp` replaces `main.cpp`.** It starts the same first state. In a browser
  `Application::run` does not return, and everything on the stack below it is destroyed before
  the first frame, so the `Application` is a `static` rather than a local variable. A failure is
  written to the browser's console and passed to the page, because a page has no message box.
- **`SUFFIX ".html"`** makes the build write `MyGame.html`, with `MyGame.js` and `MyGame.wasm`
  beside it.
- **`--embed-file`** packs everything in `game/content` into the module, at the paths the
  Windows build copies it to, so `load_manifest("./manifest.json")` finds the same files.
- **`--shell-file`** makes the page from `web/shell.html`. Emscripten puts the module's script
  where the page says `{{{ SCRIPT }}}`.
- **The rules' tests run under Node**, which Emscripten's toolchain gives ctest. The start-up
  check is not in this branch, because it needs a command line and a page has none.

<Steps>

1. **Configure the browser build**, in the prompt where you ran `emsdk_env.bat`, in
   `C:\dev\mygame`. This is needed once:

   ```bat
   cmake --preset wasm-debug
   ```

   **The first browser configure can take a quarter of an hour**, sitting for minutes at
   `Fetching registry information from https://github.com/microsoft/vcpkg (HEAD)...` or at
   `Detecting compiler hash for triplet x64-windows...` with nothing else happening; leave it
   running. Where this page was checked, the first configure took 860 seconds in one fresh
   project, 297 in another and 11 in a third; later configures take seconds. vcpkg builds doctest, the tests' library, again for WebAssembly, and
   prints its usual lines. The configure also prints this warning
   three times, which does not matter, because the game uses no shared libraries:

   ```text title="Output"
   CMake Warning at C:/dev/emsdk/upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake:26 (message):
     This version of cmake (4.3.1-msvc1) does not support emscripten shared
     libraries.  Use cmake < 4.2.0 or cmake > 4.3.3 if you need shared library
     support
   ```

   It ends:

   ```text title="Output"
   -- Configuring done (11.1s)
   -- Generating done (0.1s)
   -- Build files have been written to: C:/dev/mygame/out/build/wasm-debug
   ```

   The time on the `Configuring done` line is your own. If it stops with `include could not find requested file:`, `emsdk_env.bat` has not
   run in this prompt: see [If something fails](#if-something-fails).

2. **Build it and run its test:**

   ```bat
   cmake --build --preset wasm-debug && ctest --preset wasm-debug
   ```

   The first build compiles the engine with Emscripten's compiler, clang, in 92 steps, and took
   9 seconds here; expect a minute or more on a slower machine. It ends as below, with the two
   `Linking` lines in either order:

   ```text title="Output"
   [90/92] Building CXX object game/CMakeFiles/MyGameTests.dir/tests/motion_tests.cpp.o
   [91/92] Linking CXX executable game\MyGameTests.js
   [92/92] Linking CXX executable game\MyGame.html
   Test project C:/dev/mygame/out/build/wasm-debug
       Start 1: MyGameTests
   1/1 Test #1: MyGameTests ......................   Passed    0.15 sec

   100% tests passed, 0 tests failed out of 1

   Total Test time (real) =   0.17 sec
   ```

   The page is three files in `out\build\wasm-debug\game`: `MyGame.html` (2 KB), `MyGame.js`
   (270 KB) and `MyGame.wasm` (11 MB, a debug build; the release one below is under 400 KB). The
   folder `out\build\wasm-debug` takes about 60 MB.

   If the build ends `ninja: build stopped: subcommand failed.`, find the first `error:` line
   above it. Clang's errors look a little different from Visual Studio's:
   [In the browser build](/docs/get-started/build-errors/#in-the-browser-build) reads one. A test
   failure looks as on Windows.

</Steps>

## Serve it and open it

A browser will not run a WebAssembly module from a file opened by double-clicking: opened that
way the page stays at `Loading...`. It has to come from a web server, and the Python that came
with Emscripten has one. Start it in a window of its own, from the prompt in `C:\dev\mygame`:

```bat
start "MyGame server" "%EMSDK_PYTHON%" -m http.server 8000 --bind 127.0.0.1 --directory out\build\wasm-debug\game
```

A new window titled **MyGame server** opens and prints:

```text title="Output"
Serving HTTP on 127.0.0.1 port 8000 (http://127.0.0.1:8000/) ...
```

and your prompt is free for the next command. Leave that window open: the server runs until you
close it. If the window closes at once, the server could not start; run the same command
without `start "MyGame server"` to read why in your prompt, as in [If something
fails](#if-something-fails). Now open **`http://127.0.0.1:8000/MyGame.html`** in Chrome, Edge or Firefox. The page
shows the same greeting as the Windows build in a black box, with a line of help below it, and
the same keys work once you click the game. The server's window prints a line for each file the
browser asks for: `200` when it was sent, and on a later visit `304` when the browser's copy was
still current:

```text title="Output"
127.0.0.1 - - [31/Oct/2026 04:12:31] "GET /MyGame.html HTTP/1.1" 200 -
127.0.0.1 - - [31/Oct/2026 04:12:31] "GET /MyGame.js HTTP/1.1" 200 -
127.0.0.1 - - [31/Oct/2026 04:12:31] "GET /MyGame.wasm HTTP/1.1" 200 -
127.0.0.1 - - [31/Oct/2026 04:12:31] code 404, message File not found
127.0.0.1 - - [31/Oct/2026 04:12:31] "GET /favicon.ico HTTP/1.1" 404 -
```

The `404` for `favicon.ico` is the browser asking for a tab icon the page does not have, and is
harmless. Opened without `MyGame.html`, `http://127.0.0.1:8000/` shows *Directory listing for
/*, the build folder's files; click `MyGame.html` there. Because of `--bind 127.0.0.1`, only this
machine can reach the server. If a browser is ended abruptly, the window can print a
`Traceback` ending `ConnectionResetError: [WinError 10054] An existing connection was forcibly
closed by the remote host`; that is harmless, and the server goes on serving.

Sound starts after your first key press or click on the page, which is a browser rule. To stop
the server, close the **MyGame server** window, or click in it and press **Ctrl+C**, which prints
`Keyboard interrupt received, exiting.`

<Aside title="Without start">
The same command without `start "MyGame server"` runs the server in this prompt, which then
does nothing else until you press Ctrl+C. To build while it runs, open a second x64 Native Tools
Command Prompt and run `C:\dev\emsdk\emsdk_env.bat` and `cd /d C:\dev\mygame` in it first.
</Aside>

## Change it, rebuild and refresh

With the server still running, change the game as in
[Make a first change](/docs/get-started/first-change/), for example the greeting in
`game\states\hello_state.cpp`. Then, in the prompt:

```bat
cmake --build --preset wasm-debug && ctest --preset wasm-debug
```

A one-file change is three steps, compiling that file and linking the page, and took 8 seconds
here. The server does not need restarting; it sends whatever is in the folder.

**Then reload the page with Ctrl+F5, not F5.** The server does not tell the browser how long it
may keep a file, so the browser guesses, and F5 asks the server again only for `MyGame.html`: it
keeps the old `MyGame.js` and `MyGame.wasm` and runs the old game. The server's window shows it:
after F5 only `GET /MyGame.html` appears, and after Ctrl+F5 all three files. When this page was
checked, Chrome and Edge kept the old game through F5, a second F5 20 seconds later and opening the
address again, and Ctrl+F5 loaded the new one. Ctrl+F5 is the full reload in Edge and Firefox
too.

### When you add a file

The browser build has its own list of the game's `.cpp` files and its own list of the content
files that make it link again:

- **A new `.cpp` file** goes in both `add_executable(MyGame` lists in `game\CMakeLists.txt`, the
  one inside `if(EMSCRIPTEN)` and the Windows one. Without it the Windows build works and this
  one stops with `wasm-ld: error: ... undefined symbol`. [Add a screen to your
  game](/docs/guides/your-screen/) does it step by step.
- **A new content file**, such as a picture, a sound or a font, needs no copy line, because
  `--embed-file` packs the whole `game\content` folder. It does need a line in the
  `LINK_DEPENDS` list inside `if(EMSCRIPTEN)`, beside the `.spritefont` line. Without it, a change
  to that file alone does not rebuild the page, and the page keeps the old picture or sound.
  [Put a picture in your game](/docs/guides/your-picture/) gives the line.
- **`web\shell.html`, `content\manifest.json` and the starter's font** are in that list already:
  a change to any of them rebuilds the page.

## Check the page loads and quits

Labrador's page runner opens your page in a hidden browser, lets it draw, presses keys and
checks that it quits with nothing in the console. It is the check CI runs on the starter
project's page, and it takes about ten seconds. It needs the full path of Chrome or Edge; check
that the one you have is there:

```bat
dir "C:\Program Files\Google\Chrome\Application\chrome.exe"
dir "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
```

Each prints the file's date and size if it is there, or `File Not Found`. Every Windows 11
machine has Edge. Set `browser` to one that is there, Chrome:

```bat
set "browser=C:\Program Files\Google\Chrome\Application\chrome.exe"
```

or Edge:

```bat
set "browser=C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
```

Then, in the prompt where you ran `emsdk_env.bat`, in `C:\dev\mygame`:

```bat
"%EMSDK_NODE%" "external\labrador\tests\render\web\run_page.mjs" ^
  --browser "%browser%" ^
  --page out\build\wasm-debug\game\MyGame.html ^
  --quit-keys Escape,Enter --timeout 60
echo %errorlevel%
```

The runner starts its own web server and a browser with a temporary profile, and closes both
when it finishes; it does not need the **MyGame server** window. It waits for the game to
start, lets 60 frames draw, presses Escape and then Enter, and waits for the page's
`Module.onQuit` callback. A pass, here with Edge, prints:

```text title="Output"
run_page: 60 animation frames
run_page: pressed Escape
run_page: pressed Enter
run_page: Module.onQuit was called
run_page: browser: Edg/156.0.4314.50 (DevTools 1.3, revision @af2ba23ae0ecf7084d900446fc59d5119dd5fd5e)
run_page: WebGL2 renderer: ANGLE (NVIDIA, NVIDIA GeForce RTX 5080 (0x00002C02) Direct3D11 vs_5_0 ps_5_0, D3D11)
0
```

with your own browser's version and graphics card. **A pass is the `0` at the end.** A console
error or warning, a failed assertion, an uncaught exception, a browser warning or error, or a call
to `Module.onError` fails the run and prints the message, even if the page also quits; the last
line is then `1`. A missing `Module.onQuit` fails, and a page that never starts or quits stops
after the 60 seconds. If you change the game's quit keys, change `--quit-keys` to match: it
takes `Escape`, `Enter`, `Space`, the four `Arrow` directions, and `KeyA` to `KeyZ`. This checks
start-up and the quit path; it does not compare pictures or replace playing the game.

To see a failure, add `console.error("deliberate page-check failure");` just after the opening
`<script>` tag in the built `out\build\wasm-debug\game\MyGame.html` and run the same command: it
prints that message and `1`. A build with no source change does not replace the file: it prints
only `[1/1] Checking that no engine file includes a game header`, and the check fails again. To
put it right, delete the page and build again:

```bat
del out\build\wasm-debug\game\MyGame.html
cmake --build --preset wasm-debug
```

The build ends `[2/2] Linking CXX executable game\MyGame.html`, and the check passes again.

## The release page

`wasm-debug` is for trying the game: its module is large and slow to start. `wasm-release` is
the one to give people. It builds the same way, into its own folder:

```bat
cmake --preset wasm-release
cmake --build --preset wasm-release && ctest --preset wasm-release
```

Here the configure took 9 seconds and the build 10, again 92 steps, ending as in the debug build
with `100% tests passed, 0 tests failed out of 1`. The page is in `out\build\wasm-release\game`:
`MyGame.html` (1 KB), `MyGame.js` (117 KB) and `MyGame.wasm` (379 KB). Serve it as above with
`out\build\wasm-release\game` in place of `out\build\wasm-debug\game`, after closing the first
server, or with `8001` in place of `8000` in the command and the address.

[Put your game on the web](/docs/guides/your-web-page/) builds, gathers and publishes the
release with one script. The next section is what that script does, by hand.
[Put your game on a web host](/docs/guides/web-host/) says what any host must send with the
files.

## Gather the browser release and its notices

The template's build writes the page, script and module; it does not gather their notices.
After building `wasm-release`, run this in `C:\dev\mygame`, in the prompt where you ran
`emsdk_env.bat`. It uses Labrador's bundler and the Node that came with Emscripten; there is
nothing else to install.

First put Microsoft's licence for the engine's timer code in your game's `web` folder. The
engine inside your project has a copy:

```bat
copy external\labrador\tools\web_bundle\Microsoft-LICENSE.txt game\web\
```

It prints `1 file(s) copied.` Keep the file with your game and reuse it for later releases. If
it prints `The system cannot find the file specified.`, your engine is older than this file,
such as the `v0.2.0` pin of the Git route; fetch the same text from this fixed upstream
revision instead:

```bat
curl.exe --fail --location https://raw.githubusercontent.com/microsoft/DirectXTK/a0a1ab67d9d8f1a41b76c0950eb37f27d6bf355d/LICENSE --output game\web\Microsoft-LICENSE.txt
```

**The bundler empties `out\web-release` first.** Keep that folder for generated release files
only; do not point `--out` at your project, source or build folder. Paste the whole box; each
line ending `^` continues on the next, so a missed line or a space after a `^` breaks it:

```bat
set "engine=external\labrador"
set "emscripten=%EMSDK%\upstream\emscripten"
"%EMSDK_NODE%" "%engine%\tools\web_bundle\bundle.mjs" ^
  --out out\web-release ^
  --repository . ^
  --emscripten "%emscripten%" ^
  --build-type Release ^
  --file "MyGame.html=out\build\wasm-release\game\MyGame.html" ^
  --file "MyGame.js=out\build\wasm-release\game\MyGame.js" ^
  --file "MyGame.wasm=out\build\wasm-release\game\MyGame.wasm" ^
  --notice "%engine%\NOTICE" ^
  --licence "Labrador=%engine%\LICENSE" ^
  --licence "Microsoft sample code=game\web\Microsoft-LICENSE.txt" ^
  --licence "RapidJSON=%engine%\external\rapidjson\license.txt" ^
  --licence "JetBrains Mono=game\content\fonts\OFL.txt" ^
  --licence "Emscripten=%emscripten%\LICENSE" ^
  --licence "libc++=%emscripten%\system\lib\libcxx\LICENSE.TXT" ^
  --licence "libc++abi=%emscripten%\system\lib\libcxxabi\LICENSE.TXT" ^
  --licence "libunwind=%emscripten%\system\lib\libunwind\LICENSE.TXT" ^
  --licence "compiler-rt=%emscripten%\system\lib\compiler-rt\LICENSE.TXT" ^
  --licence "musl=%emscripten%\system\lib\libc\musl\COPYRIGHT"
```

It takes under a second and prints each file's size and its size compressed, roughly what a
player downloads:

```text title="Output"
  MyGame.html      1193 bytes,     525 under Brotli
  MyGame.js      119887 bytes,   27539 under Brotli
  MyGame.wasm    388334 bytes,  120166 under Brotli
  NOTICE.txt     102282 bytes,   12468 under Brotli
  from unknown
```

The last line names your project's Git commit, or says `unknown` when it is not a Git
repository, as a starter project is not. If it prints a block starting `node:fs` instead, read
its `Error:` line: `ENOENT: no such file or directory, copyfile` and a path in
`out\build\wasm-release` means the release is not built, so build it as in [The release
page](#the-release-page); `open` and a path in `game\web` means the licence file is missing, so do
the `copy` above.

Upload all five files in `out\web-release`: `MyGame.html`, `MyGame.js`, `MyGame.wasm`,
`NOTICE.txt` and `BUILD.json`. Keep a link to `NOTICE.txt` on your hosting page so players can
read it. The notices cover the template's default WebGL2/Web Audio build:

| Component | Where the notice comes from |
| --- | --- |
| Labrador, Microsoft's shared timer code and the collision routines adapted from *Real-Time Collision Detection* | The engine's `NOTICE` attribution record, its MIT `LICENSE`, and the preserved Microsoft MIT text |
| RapidJSON | The vendored `license.txt` |
| The template's JetBrains Mono atlas | The game's `content/fonts/OFL.txt`, in full even though it is also embedded with the atlas |
| Emscripten's JavaScript runtime and system libraries | `LICENSE` in the same Emscripten install that built the module |
| libc++, libc++abi, libunwind and compiler-rt | Their licence texts in that install's `system/lib`, including the LLVM Exceptions |
| The musl-derived C library and dlmalloc | musl's `COPYRIGHT`; the engine's `NOTICE` also records dlmalloc's public-domain dedication |

The generated `NOTICE.txt` starts with Labrador's third-party record and appends the full licence
texts. Identical texts are written once, with each later component pointing to the first.
`BUILD.json` records the project's Git commit and tracked dirty state, the supplied build type,
the installed Emscripten version, and the files' sizes and hashes. A failed Git lookup is
recorded as `unknown`; it still packages. Run this immediately after the release build:
the record describes the checkout when packaging, and does not prove which
sources or flags an older module used.

Windows DLLs, DirectXTK, DirectXMath, XAudio2Redist and the MSVC runtime are absent from this
browser release. The rules-test framework, doctest, is used only by the test program, and
lodepng only by the engine's render tests. Neither test program is in the folder you upload.

Your game's own code and content have their own terms. Add a `--licence "Your game=LICENSE"`
argument if you have a licence file to include, and add the notices of any libraries or content
you introduce. If you replace the font, change its licence argument too. If you change the
allocator or toolchain, recheck its notice inputs against that build. Read the licence texts
for their terms; the command assembles the template's inputs and does not choose your game's
licence. Rebuild and rerun it when the engine pin, toolchain or content changes.

## The page, and what it owes the module

`web/shell.html` is yours to change. Its title, its status line and its styles are the minimal
sample's, and you replace them with your own. Set `Module` before Emscripten's generated script
starts the game. The template supplies a canvas and two of the four optional page callbacks:

<SourceFile path="samples/minimal/web/shell.html" from="var Module = {" to="};" lang="js" />

**`Module.canvas` must be the actual canvas element**, present before the game starts. The page
owns its place in the DOM and its size in CSS; the engine follows that size and the device pixel
ratio when setting the drawing buffer. Keep `tabindex="0"` on the canvas so it can take keyboard
focus, and `touch-action: none` so a finger on it does not scroll the page. Call `canvas.focus()`
when the player starts playing, as the template does.

The four callbacks below are optional. **Names are exact and case sensitive.** A misspelled name
is silently ignored, with no warning; a value that is not a function is ignored too. The engine
reads each callback from `Module` when it is due.

| Callback | When it is called | What the page can show |
| --- | --- | --- |
| `Module.onQuit()` | The game calls `Application::quit()` (or closes its `Window`), after the frame loop has been cancelled and the window's input and page listeners have been removed. The `Application` releases its states and services on a later task. It has no arguments. | The game has ended; offer a reload or another game. |
| `Module.onError(message)` | The template's `main_web.cpp` forwards a startup exception, or the browser window catches an exception from a frame or input handler. `message` is a string, also written to the console. A caught frame or input failure stops the loop and window listeners before this call. | The reason the game could not start or continue. |
| `Module.onContextLost()` | The renderer observes a lost WebGL2 context, once per loss, at the next `begin_frame`. It has no arguments. | Graphics are unavailable and restoration is awaited. |
| `Module.onContextRestored()` | At `begin_frame`, after the renderer and the game's device resources have been rebuilt. It has no arguments; that frame can now draw again. | Remove the graphics-loss message. |

Keep the startup error forwarding in `main_web.cpp` when you change the entry point. A script,
fetch or WebAssembly compilation failure can happen before the engine runs, so the page must
handle loader failures separately; `onError` cannot report every failure to load the module.

The context callbacks run from a frame, rather than directly from the browser's context events.
Loss is reported before restoration, even if both happen between two frames. Restoration has no
deadline: if the browser never restores the context, `onContextRestored` never arrives and the
canvas stays blank. Keep the loss message visible until restoration or a new page load.

### Quit before removing the canvas

**Keep the same canvas attached while the game is running.** Removing it from the DOM does not
stop the frame loop, release the WebGL2 context or unregister the window's listeners. It leaves
a hidden running game. Changing `Module.canvas` is not a way to stop or move that game either.

Before replacing or removing the canvas, arrange for the game to call `Application::quit()` and
wait for `onQuit`. The template's Escape/Enter confirmation is one way to reach it. There is no
built-in JavaScript stop function; a host that needs a stop button must connect it to its own
game's quit path.

Quit cancels the loop and removes the window's listeners. On the next browser task the static
`Application` destroys its states and releases its services, the WebGL2 context and Web Audio
included, as its destructor would on Windows. Nothing may call into the game after `onQuit`.
Reload the template's page to play again. An ES-module host such as LineSweeper's creates a fresh
module instance and a fresh canvas for each game, then drops the old canvas after quit, so a
finished instance can be collected.

## If something fails

### Installing Emscripten

<Aside type="caution" title="'git' is not recognized as an internal or external command, operable program or batch file.">
You ran `git clone` without Git installed. Use step 2's `curl` and `tar` lines instead, which
need no Git.
</Aside>

<Aside type="caution" title="'python' is not recognized as an internal or external command, operable program or batch file.">
From `emsdk install`: emsdk's first run needs Python, and there is none on your `PATH`. Do step 1,
open a new prompt, and run `cd /d C:\dev\emsdk` and `emsdk install` again. Once installed,
Emscripten brings its own Python and `emsdk` no longer needs yours.
</Aside>

<Aside type="caution" title="Python was not found; run without arguments to install from the Microsoft Store...">
`python` is Windows' shortcut to the Store, not Python. Install Python as in step 1, then open a
new prompt.
</Aside>

<Aside type="caution" title="error: emsdk requires python 3.10 or above">
From `emsdk install`, followed by the path and version of the Python it found: that Python is too
old for emsdk. Install a current one as in step 1, open a new prompt, check that `python
--version` prints `Python 3.10` or later, and run `cd /d C:\dev\emsdk` and `emsdk install` again.
If it still prints the old version, the old Python comes first on your `PATH`: uninstall it in
**Settings > Apps > Installed apps** and open a new prompt.
</Aside>

<Aside type="caution" title="curl: (6) Could not resolve host: github.com">
No internet connection, or a network that blocks GitHub. Connect and run step 2's box again.
`curl: (22) The requested URL returned error: 404` instead means the address in the box was
changed: paste the box again as it is.
</Aside>

<Aside type="caution" title="A duplicate file name exists, or the file cannot be found.">
From `ren`: there is already a `C:\dev\emsdk`, from an earlier try. If that earlier try
finished, use it and skip to step 3. Otherwise delete both folders and do step 2 again:
`rmdir /s /q C:\dev\emsdk` and <code>rmdir /s /q C:\dev\emsdk-{EMSDK_VERSION}</code>. With Git, the same mistake
gives `fatal: destination path 'emsdk' already exists and is not an empty directory.`
</Aside>

<Aside type="caution" title="tar: Error opening archive: Failed to open 'emsdk.zip'">
The download did not happen, or the prompt is not in `C:\dev`. Run step 2's box again from its
first line, and read `curl`'s output.
</Aside>

<Aside type="caution" title="'emsdk' is not recognized as an internal or external command, operable program or batch file.">
The prompt is not in `C:\dev\emsdk`. Run `cd /d C:\dev\emsdk` first; the prompt then ends
`C:\dev\emsdk>`.
</Aside>

<Aside type="caution" title="error: tool or SDK not found: '6.0.99'">
The version was mistyped. It must be {EMSDK_VERSION} exactly, as in step 3's box.
</Aside>

<Aside type="caution" title="Error: Downloading URL '...': <urlopen error ...> and error: installation failed!">
The download stopped: the connection dropped, or a firewall, proxy or antivirus blocked it. Here
it was `[WinError 10061] No connection could be made because the target machine actively refused
it`, through a proxy that was not there. Check the connection and run `emsdk install` again. If it fails the same way twice, delete the folder with
`rmdir /s /q C:\dev\emsdk` and start again from step 2.
</Aside>

<Aside type="caution" title="error: error: tool is not installed and therefore cannot be activated: 'node-24.19.0-64bit'">
`emsdk activate` ran before `emsdk install` finished. Run step 3 again, then step 4.
</Aside>

### Building and serving

<Aside type="caution" title="include could not find requested file: /upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake">
From `cmake --preset wasm-debug`: this prompt has not run `emsdk_env.bat`, so `EMSDK`, which
should come before `/upstream`, is empty. Run `C:\dev\emsdk\emsdk_env.bat` in it and configure
again; the half-made build folder does not need deleting.
</Aside>

<Aside type="caution" title={`'"%EMSDK_PYTHON%"' is not recognized as an internal or external command, operable program or batch file.`}>
From the server command typed without `start`, or with `"%EMSDK_NODE%"` from the page runner or
the bundler: this prompt has not run `emsdk_env.bat`, as in a new prompt or the next day. With
`start`, no server window opens; a box titled `%EMSDK_PYTHON%` says `Windows cannot find
'%EMSDK_PYTHON%'. Make sure you typed the name correctly, and then try again.` Click **OK**, run
`C:\dev\emsdk\emsdk_env.bat` in this prompt, and run the command again.
</Aside>

<Aside type="caution" title="The system cannot find the path specified.">
After `C:\dev\emsdk\emsdk_env.bat`: there is no Emscripten at `C:\dev\emsdk`: do [Install Emscripten](#install-emscripten). If you
put it somewhere else, use that folder's `emsdk_env.bat`.
</Aside>

<Aside type="caution" title="'cmake' is not recognized as an internal or external command, operable program or batch file.">
The prompt is a plain Command Prompt, not the x64 Native Tools Command Prompt. Open that one, then
run `emsdk_env.bat` and `cd /d C:\dev\mygame` in it again.
</Aside>

<Aside type="caution" title="PermissionError: [WinError 10013] An attempt was made to access a socket in a way forbidden by its access permissions">
At the end of a long `Traceback`, from the server command run without `start`; with `start`, the
**MyGame server** window just closes at once. Port 8000 is taken by another program. Use another port, such as 8001, in the
command and in the address: `--directory` stays the same, `8000` becomes `8001`, and the page is
`http://127.0.0.1:8001/MyGame.html`.
</Aside>

<Aside type="caution" title="Error response: Error code: 404, Message: File not found.">
The browser shows this for `MyGame.html`, and the server's window prints `code 404, message File
not found`: the server is serving the wrong folder, because the prompt was not in
`C:\dev\mygame` when you started it, or `wasm-debug` is not built. Close the server's window,
run `cd /d C:\dev\mygame`, check that `dir out\build\wasm-debug\game\MyGame.html` lists the file,
and start the server again.
</Aside>

<Aside type="caution" title="The page shows an old version, or not the folder you served">
After a rebuild: reload with **Ctrl+F5**, as in [Change it, rebuild and
refresh](#change-it-rebuild-and-refresh). If it is still old, an older server may be answering:
a second server started on a port that one already uses prints `Serving HTTP` with no error,
and the first goes on answering, from whatever folder it serves. Close every server window,
start one, and press Ctrl+F5.
</Aside>

<Aside type="caution" title="The page stays at Loading...">
The address starts `file://`: the page was opened from Explorer. Open it from the server, at
`http://127.0.0.1:8000/MyGame.html`. Otherwise press **F12** and read the **Console**: the first
red line that is not about `favicon.ico` says what failed. [Troubleshooting](/docs/troubleshooting/#browser-builds) lists the
browser messages.
</Aside>

<Aside type="caution" title="run_page: spawn C:\Program Files\Google\Chrome\Application\chrom.exe ENOENT">
From the page runner, with `run_page: browser: unknown (DevTools did not answer)` among the other
lines and `1` at the end: there is no browser at the path in `browser`. Check it with `dir "%browser%"`,
and set it again from [Check the page loads and quits](#check-the-page-loads-and-quits).
</Aside>

<Aside type="caution" title="run_page: <your page> did not finish within 60 s">
After a minute, naming the file given to `--page`, often with `run_page: browser error: Failed to
load resource: the server responded with a status of 404`: the `--page` path is wrong, or the page never started or never
quit. Check the path with `dir out\build\wasm-debug\game\MyGame.html`, and that the prompt is in
`C:\dev\mygame`.
</Aside>

A build error in your own code is the same as on Windows, in clang's words:
[Read a build error](/docs/get-started/build-errors/#in-the-browser-build).
[Troubleshooting](/docs/troubleshooting/#browser-builds) lists this page's messages too.

<Aside title="The Windows build is unchanged">
The browser presets build into their own folders under `out\build`, so the Windows build and its
two tests are exactly as before. [Check your game in CI](/docs/guides/ci/) builds only the Windows
preset.
</Aside>

## What players need

A current Chrome, Edge, Firefox or Safari with WebGL2, on a computer. The browser build has been
checked in desktop Chrome and Edge and, for LineSweeper's page, Firefox. It has not been checked
in Safari, on a phone, with a real touchscreen or with a physical gamepad.
[Platform support](/why/#platform-support) says where each of those stands; say the same on your
own page until you have checked them yourself.
