The engine comes with six [samples](/examples/): the minimal sample, LineSweeper, and the
collision, audio, local multiplayer and components examples. The Collision, Audio and Local
multiplayer guides each run one, and the rest of the guides quote their code. This page is
where every one of them is run from.

The samples are not part of your game. They are in the engine's own folder, and your game's
build does not build them: `cmake --build --preset x64-debug` in your project folder makes
`MyGame.exe` and its tests, and nothing else. To get the samples you run the engine's own
build, in the engine's folder. It makes a second build folder there and does not change your
game.

## Where to run this

Every command on this page, and every sample command in the guides, runs in the engine's folder,
in the x64 Native Tools Command Prompt from [Install the tools](/docs/get-started/prerequisites/):

| You have | The engine's folder |
| --- | --- |
| The [starter project](/docs/get-started/starter/), extracted to `C:\dev\mygame` | `C:\dev\mygame\external\labrador` |
| A clone from [Build Labrador](/docs/get-started/build-labrador/) | `C:\dev\Labrador` |

The boxes below use the starter project's folder. On the Git route, use `cd /d C:\dev\Labrador`
in place of the first line. Build Labrador has already built every sample, so on that route you
can go straight to [Start a sample](#start-a-sample).

If your project is somewhere other than `C:\dev\mygame`, the engine's folder is your project's
folder followed by `\external\labrador`.

## Build them

<Steps>

1. **Go to the engine's folder:**

   ```bat
   cd /d C:\dev\mygame\external\labrador
   ```

   The prompt ends `C:\dev\mygame\external\labrador>`. Check that you are in the right place:

   ```bat
   dir /b samples
   ```

   It lists six folders: `audio`, `collision`, `components`, `linesweeper`, `local_multiplayer`
   and `minimal`. If `cd` answers `The system cannot find the path specified.`, your project is
   not in `C:\dev\mygame`: use your project's folder followed by `\external\labrador`.

2. **Configure the engine's build:**

   ```bat
   cmake --preset x64-debug
   ```

   This is the same preset name as your game's, but here it configures the engine as a project
   of its own, with its samples and tests, into `out\build\x64-debug` inside the engine's folder.
   vcpkg reuses the packages it built for your game and adds one more, lodepng, which the
   engine's tests use. On a fast desktop this took 10 seconds; a slower machine, or one where
   vcpkg has to build lodepng, takes longer.

   It has worked when the last lines are these:

   ```text title="Output"
   -- Configuring done
   -- Generating done
   -- Build files have been written to: C:/dev/mygame/external/labrador/out/build/x64-debug
   ```

   CMake also prints a time in brackets after each `done`. If it ends with `Configuring
   incomplete, errors occurred!`, the messages are the same as the ones in
   [Build Labrador's If something fails](/docs/get-started/build-labrador/#if-something-fails).
   Those fixes are written for a clone: where they say `C:\dev\Labrador` or the `Labrador`
   folder, use `C:\dev\mygame\external\labrador`, whose prompt ends `external\labrador>`.

3. **Build everything:**

   ```bat
   cmake --build --preset x64-debug
   ```

   This builds the engine, all six samples, the engine's tests and its benchmarks: 326 steps,
   which took 19 seconds on the same desktop. Ninja numbers each step, and a build that worked
   stops at the last number, such as `[326/326] Linking CXX executable tests\app\AppTests.exe`,
   with no line saying `FAILED`. Your total and the last file may differ.

   The engine's build folder comes to about 1 GB. It is separate from your game's
   `C:\dev\mygame\out`.

4. **Optionally, run the engine's tests:**

   ```bat
   ctest --preset x64-debug
   ```

   It should end `100% tests passed, 0 tests failed out of 20`, after about 20 seconds. These
   are the engine's tests, not your game's; your game's two are still run from `C:\dev\mygame`.

</Steps>

## Start a sample

From the engine's folder, start a sample by its path. For the collision sample:

```bat
out\build\x64-debug\samples\collision\CollisionSample.exe
```

The prompt is ready again as soon as the window opens, and the sample keeps running until you quit
it. Each sample copies its content beside its `.exe`, so it starts from any folder: from
another prompt, give the whole path, such as
`C:\dev\mygame\external\labrador\out\build\x64-debug\samples\collision\CollisionSample.exe`.

| Sample | Start it with | To quit | More |
| --- | --- | --- | --- |
| Minimal | `out\build\x64-debug\samples\minimal\MinimalSample.exe` | Escape, then Enter | [Run the minimal sample](/docs/get-started/run-minimal/) |
| LineSweeper | `out\build\x64-debug\samples\linesweeper\LineSweeperSample.exe` | Escape, Down to **QUIT**, Enter | [Examples](/examples/#controls) |
| Collision | `out\build\x64-debug\samples\collision\CollisionSample.exe` | Escape | [Collision](/docs/guides/collision/) |
| Audio | `out\build\x64-debug\samples\audio\AudioSample.exe` | Escape | [Audio](/docs/guides/audio/) |
| Local multiplayer | `out\build\x64-debug\samples\local_multiplayer\LocalMultiplayerSample.exe` | Escape | [Local multiplayer](/docs/guides/local-multiplayer/) |
| Components | `out\build\x64-debug\samples\components\ComponentsGallery.exe` | Escape | [Examples](/examples/#components-the-pieces-you-copy) |

Your game started as a copy of the minimal sample. LineSweeper's pause menu has **RESUME**,
**RESTART**, the colours row and **QUIT**; Up and Down move between them. Once the board fills
and it says **TOPPED OUT**, Escape does nothing: press R to start a new match first. To hear the audio
sample, Windows needs a working sound output, such as speakers or headphones.

## Building one sample

The guides build only the sample they are about, which is quicker than building everything the
first time. In the engine's folder, after step 2 of [Build them](#build-them) has configured it:

```bat
cmake --build --preset x64-debug --target CollisionSample CollisionSampleTests
```

On the same desktop, straight after configuring, this took 100 steps and 9 seconds.

A target is one program in the build. Each sample's target is the name of its `.exe` without
`.exe`. Their tests have targets of their own, which do not all follow one pattern:
`MinimalTests`, `LineSweeperTests`, `CollisionSampleTests`, `AudioSampleTests`,
`LocalMultiplayerTests` and `ComponentsTests`. Building everything once, as above, makes every
target, and later builds only redo what changed.

## LineSweeper's match replays

LineSweeper's rules tests play whole matches with no window. Its
<RepoLink path="samples/linesweeper/README.md" hash="running-the-rules-tests">README</RepoLink>
runs them under the `x64-debug-null` preset, which draws nothing and needs no graphics card. In
the engine's folder:

```bat
cmake --preset x64-debug-null
cmake --build --preset x64-debug-null --target LineSweeperTests
ctest --preset x64-debug-null -R "^LineSweeperTests$" --output-on-failure --no-tests=error
```

On the same desktop the three took 21 seconds, and the last ends
`100% tests passed, 0 tests failed out of 1`. They make a second build folder,
`out\build\x64-debug-null`, beside the first.

## Changing a sample

The samples are yours to change and break: your game's build does not compile anything in
`external\labrador\samples`. Before you change one, keep a copy of them all. In the engine's
folder:

```bat
xcopy samples C:\dev\samples-backup /E /I /Q
```

It prints `140 File(s) copied`, or a similar count. Edit a sample's files, run the build from
the engine's folder again, and start it again. To put one file back, name it, starting
`samples\`, then copy it back and give it the current time, as
[Make a first change](/docs/get-started/first-change/) explains for your game:

```bat
set "FILE=samples\collision\body.cpp"
copy /y "C:\dev\samples-backup\%FILE:samples\=%" "%FILE%" && copy /b "%FILE%" +,, "%FILE%"
```

It prints `1 file(s) copied.` twice; then build again.

Changes to a sample stay in this project's `external\labrador` only.
[Put your project in Git](/docs/guides/starter-to-git/) and
[Move a starter project to a newer Labrador](/docs/guides/starter-update/) both replace that
folder, so keep anything you want from a sample somewhere else first.

Do not edit files in `external\labrador\engine`. That folder is the engine your game builds, so
a change there changes your game too.

## Getting the space back

The engine's build folder can be deleted whenever you no longer need the samples. From the
engine's folder:

```bat
rmdir /s /q out
```

`rmdir /s /q` deletes the folder and everything in it without asking, so check that the prompt
ends `external\labrador>` first. It deletes only what this page's build made. Your game, its
build and the engine's source are untouched, and the build steps above make it again.

## If something fails

<Aside type="caution" title="ninja: error: unknown target 'CollisionSample'">
The command ran in your project's folder, `C:\dev\mygame`, whose build makes only your game. Go
to the engine's folder with `cd /d C:\dev\mygame\external\labrador`, then configure and build
there as in [Build them](#build-them).
</Aside>

<Aside type="caution" title="Error: C:/dev/mygame/external/labrador/out/build/x64-debug is not a directory">
The build ran before the engine's build was configured, or after a configure that failed. Run
`cmake --preset x64-debug` in the engine's folder, as in step 2 of [Build them](#build-them),
until it ends `-- Build files have been written to:`, then build again.
</Aside>

<Aside type="caution" title="The system cannot find the path specified.">
Starting a sample gave this, or `is not recognized as an internal or external command`. Either
the prompt is not in the engine's folder, or the build has not finished. Check the prompt ends
`external\labrador>`, run `cmake --build --preset x64-debug` again and read its last lines.
</Aside>

<Aside type="caution" title="'cmake' is not recognized as an internal or external command">
The command prompt is not the x64 Native Tools Command Prompt. Open that one as in
[Install the tools](/docs/get-started/prerequisites/), go back to the engine's folder and run the
command again.
</Aside>

Any other message: [Troubleshooting](/docs/troubleshooting/) lists them, and
[Read a build error](/docs/get-started/build-errors/) shows how to find the line that matters.

## In a browser

LineSweeper plays in a desktop browser at
[the hosted demo](https://mattharding.dev/demo/linesweeper/), with nothing to build. Building
the samples for a browser needs Emscripten as well; [Build for the browser](/docs/guides/browser/)
installs it. Under a `wasm-debug` preset, from the same engine folder, each sample is a page
such as `out\build\wasm-debug\samples\collision\CollisionSample.html` instead of an `.exe`, with
its content packed into the module. Serve the folder over HTTP and open the page, as
[Serve it and open it](/docs/guides/browser/#serve-it-and-open-it) shows.
