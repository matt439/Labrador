A project made from the [starter ZIP](/docs/get-started/starter/) holds the engine as a plain
folder, `external\labrador`, at the release it came with. Nothing moves it for you. To take a
newer release, you download that release's starter ZIP, put your `game` folder into it, and
switch to it once it builds. Your old project stays as it is, under another name, until you
delete it, so a release that does not work for you costs nothing.

This is safer than replacing `external\labrador` by itself, because the project's own files
(`CMakeLists.txt`, `CMakePresets.json` and above all `vcpkg.json`, which pins the engine's
libraries) must match the engine, and the new ZIP has them matching.

If your project is in Git with the engine as a submodule, because you followed
[Start your own project](/docs/get-started/your-project/) or
[Put your project in Git](/docs/guides/starter-to-git/), use
[Move your engine pin](/docs/guides/move-pin/) instead.

The commands run in the x64 Native Tools Command Prompt. They assume your project is
`C:\dev\mygame`; if yours has another name, put it in place of `mygame` wherever a command has
`C:\dev\mygame`. Close Visual Studio, your game, and any File Explorer window showing the
project before you start.

<Steps>

1. **See which release you have.**

   ```bat
   type C:\dev\mygame\README.txt
   ```

   The line `Labrador version:` names it, for example `v0.3.0`.

2. **Download the newest starter ZIP** into `C:\dev`.

   <StarterDownload part="download" />

   If its version is the one you already have, there is nothing newer and you can stop here.

3. **Extract it beside your project**, into a new folder `C:\dev\new`:

   <StarterDownload part="update" />

   The new project is now `C:\dev\new\mygame`. If `mkdir` says
   `A subdirectory or file C:\dev\new already exists.`, a folder is left from an earlier move:
   look in it, delete it with `rmdir /s /q C:\dev\new` if you no longer need it, and run the box
   again.

4. **Read what changed.** Every change in the engine that a game can notice is an entry in
   CHANGES.md, under the heading of the release that made it, with what to do about it when
   there is something to do. Open the new release's copy:

   ```bat
   notepad C:\dev\new\mygame\external\labrador\CHANGES.md
   ```

   Read every heading above the one for your release, then close Notepad. The template your
   `game` folder was copied from keeps its own list of changes, newest first and dated, of what
   a copy taken earlier would want:

   ```bat
   notepad C:\dev\new\mygame\external\labrador\samples\minimal\README.md
   ```

   Its list is under *A copy is yours*. Read the entries dated after your release, which is the
   date beside your release's heading in CHANGES.md. Neither list needs anything from you
   unless an entry says so; note the ones that do for step 7.

5. **Put your game into the new project.** These lines delete the new project's copy of the
   template and copy your `game` folder in its place:

   ```bat
   rmdir /s /q C:\dev\new\mygame\game
   xcopy C:\dev\mygame\game C:\dev\new\mygame\game /E /I
   ```

   Check the first line before you run it: it must name `C:\dev\new\mygame\game`, the new
   copy, and not your own. `xcopy` lists each file it copies and ends with a count such as
   `15 File(s) copied`.

6. **Compare the project's own files.** Run these four lines. Each compares a file in your
   project with the new project's:

   ```bat
   fc C:\dev\mygame\CMakeLists.txt C:\dev\new\mygame\CMakeLists.txt
   fc C:\dev\mygame\CMakePresets.json C:\dev\new\mygame\CMakePresets.json
   fc C:\dev\mygame\vcpkg.json C:\dev\new\mygame\vcpkg.json
   fc C:\dev\mygame\external\labrador\website\src\walkthrough\game-CMakeLists.txt C:\dev\new\mygame\external\labrador\website\src\walkthrough\game-CMakeLists.txt
   ```

   `FC: no differences encountered` means the file is the same in both. A list of lines
   between `*****` markers means it differs:

   - For the first three, the new project's file is the one to keep, because it matches the
     new engine. If you changed one of them yourself, for example to add a library to
     `vcpkg.json`, open both with Notepad and make your change again in the new one.
   - The fourth compares the template's `game\CMakeLists.txt` at the two releases. If it
     differs, the release changed that file, and your own `game\CMakeLists.txt`, which you
     just copied across, does not have the change yet.

     Find out whether you ever changed your `game\CMakeLists.txt`, for example to add a source
     file or a library, by comparing it with the template it started from:

     ```bat
     fc C:\dev\mygame\game\CMakeLists.txt C:\dev\mygame\external\labrador\website\src\walkthrough\game-CMakeLists.txt
     ```

     If that prints `FC: no differences encountered`, you never changed it, and the new
     release's copy can simply replace it:

     ```bat
     copy /y C:\dev\new\mygame\external\labrador\website\src\walkthrough\game-CMakeLists.txt C:\dev\new\mygame\game\CMakeLists.txt
     ```

     It prints `1 file(s) copied.` If the comparison did list differences, those are your own
     changes: open the new copy with `notepad C:\dev\new\mygame\game\CMakeLists.txt` and make
     the changes the fourth comparison above shows, using CHANGES.md and the template's list
     from step 4 to see why each was made.

7. **Make the changes step 4 asked for**, if any, in `C:\dev\new\mygame\game`.

8. **Swap the folders.** This renames your project to `mygame-old` and moves the new one to
   `C:\dev\mygame`:

   ```bat
   cd /d C:\dev
   ren C:\dev\mygame mygame-old
   move C:\dev\new\mygame C:\dev\mygame
   rmdir C:\dev\new
   cd /d C:\dev\mygame
   ```

   `move` prints `1 dir(s) moved.` If `ren` says
   `The process cannot access the file because it is being used by another process.`, a
   window still has the project open, often another command prompt that is in it, Visual
   Studio, or Explorer: close it and run the box again. If it says
   `A duplicate file name exists, or the file cannot be found.`, a `mygame-old` is left from an
   earlier move; delete it with `rmdir /s /q C:\dev\mygame-old` once you are sure you do not
   need it, and run the box again.

9. **Configure, build, test and play**, in the new project:

   ```bat
   cmake --preset x64-debug
   cmake --build --preset x64-debug
   ctest --preset x64-debug
   out\build\x64-debug\game\MyGame.exe
   ```

   The new project has no build folder yet, so this is a first build: configure installs
   whatever a changed `vcpkg.json` needs, which can take a few minutes. The build applies the
   engine's compiler settings to your code, warnings as errors among them, so a warning a newer
   engine causes in your code stops it; the message names the file and line. Fix your code
   there, guided by CHANGES.md, and build again.

</Steps>

## Going back

Until you delete `mygame-old`, your previous project is untouched. To use it again, rename the
new one aside and the old one back:

```bat
cd /d C:\dev
ren C:\dev\mygame mygame-new
ren C:\dev\mygame-old mygame
```

## Deleting the old project

When the new project builds, passes its tests and plays as you expect, delete the old one:

```bat
rmdir /s /q C:\dev\mygame-old
```

It deletes the folder and everything in it without asking. Any change you made to the old
project after step 5 is in that folder only, so check you have none first.

## What was checked

On 30 October 2026 the commands on this page were run as written, in a command prompt, on two
projects extracted from starter ZIPs of the same development revision, so the comparisons
found nothing to change and the rebuilt project's tests passed. No two releases with starter
ZIPs exist yet, so moving between releases that differ has not been done.
