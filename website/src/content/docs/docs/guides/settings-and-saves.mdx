Settings and progress are your game's data. Labrador's asset loaders read content; they do not
choose a save location or write a save format. Keep that code in your game, alongside the values
it understands. This example writes a small JSON settings file with a version and a volume from
0 to 100. The same file-writing code works on Windows and in Emscripten's virtual filesystem.

## Apply settings to the running game

A setting's stored value and the platform's current state can differ. The
<RepoLink path="samples/components/gallery_state.cpp">components gallery</RepoLink>
requests only **Windowed** or **Full screen**: Windows full screen is already a
borderless window, so there is no separate third mode.

### Window mode

The row's callback calls `Application::set_fullscreen`. Initialization then
seeds the row from `fullscreen()`:

	to="this->app_->fullscreen() ? 1 : 0);"
/>

`fullscreen()` reports the requested mode until the platform says otherwise.
A browser request can be deferred to an activating input event or refused,
and the player can leave full screen externally. The status line therefore
describes a request. The gallery reads the current report every tick:

<SourceFile
	path="samples/components/gallery_state.cpp"
	from="void GalleryState::update(float dt)"
	to="this->app_->fullscreen() ? 1 : 0);"
/>

`OptionRow::set_index` changes the displayed choice without calling its
callback, so re-sync does not issue another request. The gallery keeps its
Escape/B quit binding; your game chooses how leaving full screen and quitting
fit its own controls.

### Volume slider callbacks

The gallery's volume sliders illustrate callbacks and load no audio. In a
game with the [audio sample's required `tones` bank](/docs/guides/audio/#declare-a-required-bank)
already loaded, create music/effects groups in the Application's
`AudioResources` and assign sounds through its `SoundBank` at load time:

```cpp
labrador::AudioResources* audio = app->audio_resources();
const labrador::SoundGroupHandle music = audio->add_sound_group("music");
const labrador::SoundGroupHandle effects = audio->add_sound_group("effects");
labrador::SoundBank* bank = audio->sound_bank("tones");
bank->set_effect_group(bank->resolve_effect("drone_loop"), music);
bank->set_wave_group(bank->resolve_wave("ping"), effects);
bank->set_wave_group(bank->resolve_wave("chime"), effects);
audio->set_group_volume(music, 0.7f);
audio->set_group_volume(effects, 1.0f);
```

Include `engine/audio/audio_resources.h` and `engine/audio/sound_bank.h`;
`app` here points to the Application. Create each group once, then keep its
handle or resolve it by name. A group spans banks, so assign any other banks'
music/effects to those same handles.

For a copied slider ranging from 0 to 100, pass this as its `on_change`
callback, in place of the gallery's status-only callback:

```cpp
const components::Slider::Changed effects_changed = [audio, effects](int value)
{
	audio->set_group_volume(effects, static_cast<float>(value) / 100.0f);
};
```

Use the copied slider's namespace and include path in your game
(`samples/components/slider.h` in this checkout). The music slider uses the
same scaling with the music handle. Set the initial group levels to match the
sliders too: `Slider::set_value` also updates silently.

A play level of `0.8f` in an effects group set to `0.5f` reaches the device
as `0.4f`; no second volume bus is needed. A playing or paused retained effect
takes a group change immediately, a stopped effect takes it at its next play,
and a one-shot already playing keeps its old level while the next one takes
the new level. A sound assigned to no group remains at full group volume.
Keep the AudioResources and its bank alive longer than callbacks borrowing
them, as the gallery does for its Application services.

## Choose a per-user folder on Windows

Use the user's **LocalAppData** known folder, with your game's own subfolder. Do not write beside
the executable: an installed game may be in a read-only folder, and a relative path follows the
process's working directory rather than the player. The Windows API supplies a Unicode path;
`std::filesystem::path` carries it to the standard library's file streams.

<SourceFile path="tools/save_check/settings.cpp" from="std::filesystem::path settings_directory()" to="}" />

Include `windows.h` and `shlobj.h` on Windows, and link `shell32.lib` and `ole32.lib`. Replace
`MyGame` with your own stable name. In CMake, add those libraries to your game in its native
Windows branch, not its Emscripten branch:

```cmake
target_link_libraries(MyGame PRIVATE shell32 ole32)
```

## Write JSON, then check the result

The writer makes the directory, validates the value, opens the file and enables stream
exceptions. `close()` completes the standard-library write and reports a buffered write failure.
Its caller catches `std::exception` and shows a save failure; it must not tell the player the save
succeeded merely because the settings changed in memory.

<SourceFile path="tools/save_check/settings.cpp" from="void write_settings(" to="}" />

Call `write_settings(settings_directory(), 80)` when the player applies a setting. This simple
example replaces the file in place; a progress save that must survive a crash during writing
needs your game's recovery scheme, such as a second generation and a checked replacement. Keep
save writes out of the per-frame update path.

The standard library has no JSON parser. The engine reads JSON and writes none:
`engine/assets/json.h`'s `read_json_file` and `parse_json` return a document whose `JsonValue`
accessors check every kind and key, and that covers reading a save. Its parser, rapidjson, is
linked `PRIVATE` to `LabradorEngine` and no engine header names it, so your game cannot include
it through the engine. A game that writes JSON brings a writer of its own, from vcpkg or
vendored, on its own account. Read bytes with `std::ifstream`, then parse and validate them
with the reader your game chooses. Check the version, required fields, types and
ranges before applying anything. A missing settings file means defaults; malformed or unsupported
data is a reported load failure, rather than permission to silently overwrite the only copy.
The check below reads the JSON bytes in C++ and parses that tiny record in its host page;
it is a persistence example, not a general save-file parser.

## Restore browser storage before starting the game

An ordinary Emscripten file lives in memory and disappears on reload. Mount **IDBFS** at `/save`
and call `FS.syncfs(true, callback)` to populate it from IndexedDB. That operation is asynchronous.
Add a run dependency before it and remove the dependency only on success, so `main()` cannot read
defaults and overwrite an existing save while the restore is still running.

Put this JavaScript in `game/web/persist.js`:

<SourceFile path="tools/save_check/persist.js" lang="js" />

This is a `--pre-js` file, so its `FS`, `IDBFS`, `addRunDependency`, `removeRunDependency` and
`abort` names are inside Emscripten's runtime. It appends to `Module.preRun`; keep any existing
callbacks the game's host page has there. Add the file and IDBFS to the browser target's existing
link options, alongside its shell and embedded-content options:

```cmake
target_link_options(MyGame PRIVATE
    "-lidbfs.js"
    "--pre-js" "${CMAKE_CURRENT_SOURCE_DIR}/web/persist.js"
)
set_property(TARGET MyGame APPEND PROPERTY LINK_DEPENDS
    "${CMAKE_CURRENT_SOURCE_DIR}/web/persist.js")
```

The browser branch of `settings_directory()` returns `/save`. A file such as
`/save/settings.json` then uses the same `std::ofstream` writer as Windows. Keep the mount path
stable across releases: IDBFS uses that path to name its database.

## Finish the browser sync before saying saved

Closing the C++ stream updates the mounted in-memory filesystem. To persist that change, call
`Module.flushSave()` from your page after the C++ write has completed, and await its promise.
It calls `FS.syncfs(false, callback)` to copy the mounted filesystem back to IndexedDB. For
example, a page button can call an exported game function and then flush:

```js
async function applyVolume(volume) {
    if (Module._save_volume(volume) !== 0) throw new Error('Could not write settings');
    await Module.flushSave();
    // Only now show the player's saved acknowledgement.
}
```

`save_volume` is this example's `extern "C" EMSCRIPTEN_KEEPALIVE` wrapper around `write_settings`;
it returns zero on success. It is game code, not a Labrador function. Serialize save requests:
disable Apply until this promise settles, or queue the next request. Report a rejected promise
and allow a deliberate retry. Do not rely on `beforeunload` to finish an asynchronous write;
save at a checkpoint while the page is still running.

Browser storage belongs to the site's origin and browser profile. A different scheme, host or
port uses different storage. Private browsing, quota limits, eviction and clearing site data can
remove or refuse it. Keep failures visible and provide an export/import path if progress must
remain under the player's control.

## Check a real reload

<RepoLink path="tools/save_check/README.md">The complete example and check commands</RepoLink>
compile the C++ writer with this exact pre-js file and run a page in headless Chrome. The check
starts with a fresh profile, writes volume 37 through C++, awaits the sync, reloads the page at
the same origin, and asserts that C++ reads `{"version":1,"volume":37}` back before it marks the
page ready. It uses the existing browser page runner; no engine window or renderer is needed.

Use that check for storage changes, then test your game's own validation and recovery rules
separately. [Build for the browser](/docs/guides/browser/) covers the rest of the browser target;
[Content and the manifest](/docs/guides/assets/) covers the content the engine reads.
