## What each step is for

**The checkout takes the submodule.** Without `submodules`, `external/labrador` is an empty
folder and configure stops at `add_subdirectory`. When the engine's repository is private, or is
a private fork, the checkout needs a token that can read it as well.

**`VCPKG_ROOT` points at the runner's vcpkg.** Your `CMakePresets.json` reads it for the toolchain
file, as it does on your machine, and the runner image comes with a vcpkg of its own in
`VCPKG_INSTALLATION_ROOT`.

**vcpkg's binary cache is kept between runs.** Configure builds the packages your `vcpkg.json`
names, and keeps what it built in `%LOCALAPPDATA%\vcpkg\archives`, which the cache step saves
and restores. The key is your `vcpkg.json`, so a run that changes no dependency restores the
last one's binaries and configures in seconds, and the first run, or one after a dependency
changed, builds them, which took a little over a minute on a fast desktop and takes longer on a
runner.

**The MSVC environment comes from `vcvars64.bat`**, the batch file the x64 Native Tools Command
Prompt runs. It puts the compiler, CMake, Ninja and the Windows SDK's `fxc`, the shader compiler
the engine's build calls, on the path. `vswhere` finds it in whichever Visual Studio edition the
runner image has, and each step that runs CMake calls it first, because a step's environment
does not carry over to the next one.

**Configure, build and test are the commands you type.** The test step runs your project's
ctest, which holds your game's tests and none of Labrador's. The start-up check gets a Direct3D
device on the runner, which has no GPU but still offers Direct3D an adapter.

## Keep the path short

The runner checks your repository out at `D:\a\<repository>\<repository>`, and the build's object
files sit far below that. A short repository name keeps the whole path inside the 260 characters
the compiler allows, for the reason
[Choose a short folder](/docs/get-started/prerequisites/#choose-a-short-folder) gives.

## What has been checked

Labrador's own CI has a job that builds this project from the Get Started files against the
engine, and it runs most of these steps: the runner's vcpkg, vcvars found through `vswhere`,
configure, build and the game's ctest. That job takes the engine from the change being checked
rather than from a submodule, and it restores the vcpkg binary cache the engine's own Windows jobs
save without ever saving one, so it does not run this file's save step.
The file itself has run, unchanged, as the workflow of a repository of its own:
[matt439/labrador-mygame](https://github.com/matt439/labrador-mygame), which holds the project
Start your own project builds, with Labrador at `v0.2.0`. On 26 October 2026 its
[first run](https://github.com/matt439/labrador-mygame/actions/runs/40242503246) found no cache,
configured in 95 seconds, passed both tests and saved the cache, and the
[second](https://github.com/matt439/labrador-mygame/actions/runs/40242709388) restored it, so
vcpkg restored its six packages instead of building them and configure took 42 seconds. That was a hit on the exact key; the `restore-keys` fallback, for a run after `vcpkg.json` changes, has not been exercised. Each
run took about two and a half minutes on `windows-latest`, with MSVC 19.51. Both runs warn that
`actions/checkout@v4` and `actions/cache@v4` target Node.js 20, which GitHub now runs on
Node.js 24; nothing fails because of it.
