The application owns four input devices and lends them to your states: `app->keyboard()`,
`app->gamepads()`, `app->mouse()` and `app->touch()`. All four are read once at the start of
every step, before any state updates ([The tick](/docs/concepts/tick/#input-is-read-first)),
and you ask them questions from `update()`. If a build fails after you change your input code,
[Read a build error](/docs/get-started/build-errors/) shows how to read the error.

## Held, pressed and released

Every device answers the same three questions about a key or button:

| Question | Meaning |
| --- | --- |
| `held(...)` | Down now. |
| `pressed(...)` | Down now, and not down at the previous step. True for one step per press. |
| `released(...)` | Up now, and down at the previous step. |

Use `held` for anything continuous (moving, charging, scrolling) and `pressed` for anything that
happens once per press (jumping, confirming, opening a menu). Because each step compares against
the one before it, a state pushed by a press does not see that same press: the button was already
down at the previous step.

## Keyboard

Keys are named by **position**, not by the character printed on them. `Key::w`, `Key::a`,
`Key::s` and `Key::d` are the block under the left hand on any layout, which is what a movement
binding wants. The minimal sample reads arrows and WASD together:

<SourceFile path="samples/minimal/states/hello_state.cpp" from="Vector2F keyboard_direction(const Keyboard& keyboard)" to="}" />

**Typed text is separate.** `keyboard.typed()` returns what the player typed during the step, as
UTF-8, with the keyboard layout, dead keys and input methods already applied by the system. It is
valid until the next step, so copy it to keep it. Use it for a name-entry box, never for
movement.

Before displaying typed text, follow the [wide conversion and font check](/docs/guides/sprites-and-text/#from-a-string-table-to-text).
Do them when the text changes, outside `draw()`; the game's editing and
name-entry rules remain its own.

When the window loses focus, every held key is treated as released, so a character does not walk
on by itself after an alt-tab.

## Gamepads

`Gamepads` has four slots, numbered 0 to 3, and answers `held`, `pressed` and `released` with a
slot and a `GamepadButton`. The full state of a slot, sticks and triggers included, is
`state(slot)`.

On Windows the pads are read through XInput, so only XInput-compatible controllers appear;
being a USB or Bluetooth controller alone does not make one compatible. A Windows slot is
XInput's system user index. A pad keeps that slot while connected, but unplugging and plugging
it back in can give it another slot. A slot is not a persistent controller identity.

In a browser the pads come from the Gamepad API. The engine assigns each new standard-mapping
pad the lowest free engine slot, and keeps it there until it disconnects; the browser's own
gamepad index is not the engine slot. That path has been driven only by fake pads a page script
supplies in headless Chrome: no physical pad has played through it yet.

**Do not check whether a pad is connected before reading it.** An empty slot reads as a neutral
pad with nothing pressed, and `pressed` is false unless the slot was occupied at both steps.
The `connected(slot)`, `just_connected(slot)` and `just_disconnected(slot)` queries are for
decisions such as showing "Player 2, press Start" or rebinding a player after a disconnect.

### A single-player game accepts every slot

Reading only slot 0 can ignore the player's only controller: Windows can leave it in a higher
slot after another pad is unplugged. The minimal sample reads all four slots' B edges and left
sticks, alongside Escape, with no connected guard:

	from="bool quit_requested = keyboard.pressed(Key::escape);"

/>

Any pad can move the greeting or ask to quit, and any pad can answer the confirmation. Several
pads' directions add, so opposite pushes cancel; the motion rules clamp the combined direction
to one unit. That is the sample's policy. A game assigning pads to separate players instead
keeps a slot for each player and handles its disconnects; see
[Local multiplayer](/docs/guides/local-multiplayer/).

**Sticks are raw**, from −1 to 1 on each axis, with **+y pointing down** like every other
coordinate in the engine. Choosing a deadzone is the game's decision, made once with
`apply_deadzone(stick, deadzone)`. It is circular, and rescales what is left so a small push
outside the deadzone moves slowly rather than jumping to the threshold:

<SourceFile path="samples/minimal/states/hello_state.cpp" from="this->motion_ = step_motion(this->motion_," to="keyboard_direction(keyboard), dt);" />

The minimal sample's rules add the keyboard's direction to the stick's and clamp the sum, so both
work at once and neither is the "real" device:

<SourceFile path="samples/minimal/rules/motion.cpp" from="Vector2F combined_direction(" to="}" />

They take both answers as plain directions and never see a device, which is what lets a test run
them with none ([Test your game](/docs/guides/testing/)).

Triggers are read as numbers from 0 to 1, or as buttons with `trigger_held`, `trigger_pressed`
and `trigger_released`, each taking the threshold that counts as pulled.

### Vibration

`vibrate(slot, Vibration{ low_frequency, high_frequency, seconds })` sends one request to a pad's
two rumble motors. `low_frequency` is the heavy motor and `high_frequency` the light one, each a
strength from 0 to 1. A request lasts `seconds`, at most `max_vibration_seconds` (five), because
a browser plays rumble as an effect with a duration and cannot hold a level until told otherwise;
the engine stops the motors itself when the time passes, on Windows too. A new request on a slot
replaces the one running there, so a longer effect is asked for again before the last one ends.
`stop_vibration(slot)` stops it early.

A strength outside 0 to 1, a duration outside its range or a slot outside 0 to 3 throws, rather
than being clamped into something you did not ask for. An empty slot, a pad with no rumble the
platform can reach, or a game in the background is not an error: `vibrate` answers
`VibrationResult::unavailable`, and nothing waits to be sent later. `submitted` means the pad API
took the request, not that the player felt it.

The engine stops a slot's request when its pad leaves the slot, so a different pad arriving there
never inherits it, and stops every request when the game goes into the background. Coming back
replays nothing. When to stop for your own reasons, such as opening the pause menu, is your
game's call, as are the strengths, the timing and whether the player wants vibration at all.

On Windows the request goes to XInput's two motors; XInput reaches no trigger motors. In a browser
it is the Gamepad API's `dual-rumble` effect, which Chrome offers and which Firefox does not, so
there `vibrate` answers `unavailable`. **No controller has been felt vibrating through either
path yet**; the headless tests check what reaches each backend's call, not the motors.

## Binding tables

Labrador has no action-mapping layer: what each key does is your game's, written in your game.
Nor is there input capture. Reading a key never consumes it, so every reader in a frame sees the
same presses and the same text, and a developer console that wants the keyboard to itself gates
its own readers. Routing input through one place, as the table below does, is what makes that
gate one line.
For more than a handful of bindings, a table keeps it in one place. LineSweeper has nine for the
keyboard, nine for the pad and seven for the buttons it draws for a touchscreen:

and reads them into one byte per step, which is the whole of what its rules see:

LineSweeper reads `held` rather than `pressed` for these, and works out the presses inside its
rules by comparing each step's byte with the last. That keeps a recorded match replayable: the
recording carries its own presses. The
<RepoLink path="samples/linesweeper/README.md" hash="input-is-read-as-held-never-as-pressed">sample's design notes</RepoLink>
explain the choice.

## Directions for menus

Menus want "up, down, left, right" rather than a stick vector, with a repeat when a direction is
held. `pad_direction(state)` turns a pad's d-pad and left stick into a `Direction`, and
`DirectionRepeat` turns a held direction into presses: one at once, another after a delay, then
one every interval. LineSweeper's pause menu combines the keyboard and the pad, then repeats:

All four directions are read, and the menu decides what each means: up and down move the cursor,
and left and right change the piece palette on its *Colours* row.

When a menu opens while a direction is already held, call `repeat.start_held(direction)` in
`init()`: the held direction then has to be let go before it counts, so the cursor does not jump
before the menu is on screen. The [Menus guide](/docs/guides/menus/) continues from here.

## Mouse

`Mouse` answers `held`, `pressed` and `released` for `MouseButton::left`, `right`, `middle`, `x1`
and `x2`, and also reports `position()` in window pixels, `motion()` since the last step, and
`wheel()` and `wheel_horizontal()` in notches. While a button is held the mouse keeps reporting
movement outside the window, so a drag is one gesture.

A game played with a pad usually hides the pointer: `app->set_cursor_visible(false)`, or
`cursor_visible = false` in `ApplicationOptions` to hide it from the first frame. The mouse is
still read while the pointer is hidden. `set_cursor_confined(true)` keeps the pointer inside the
window on Windows while the window is active, and lets it go while the player moves or resizes the
window. A browser can lock a pointer but not confine one, so there it does nothing.

## Touch

`Touch` holds every finger on the glass, up to ten, as points with an id and a `position` in
window pixels. A point's id is handed out when it goes down and is never given to another, so
`held(id)`, `pressed(id)`, `released(id)` and `motion(id)` ask about one finger, and a map from
finger to whatever it is dragging can be keyed on it. `points()` is this step's points, in the
order they went down. A point that has been lifted is no longer in it, so finding releases walks
the step before:

```cpp
const Touch& touch = *app->touch();
for (const TouchPoint& point : touch.previous_state().active())
{
    if (touch.released(point.id))
    {
        // a finger came up at point.position
    }
}
```

A tap shorter than a step is still pressed on one step and released on the next. A point the
system takes away, or every point when the window loses the foreground, disappears without a
release. A touch is never also a mouse click, on Windows or in a browser, and a pen is the mouse.
Both paths have been driven only by simulated touch, Chrome's touch emulation in a browser and
touch injected into a window on Windows; no real touchscreen has driven either yet.
The minimal sample draws a marker with the id at every point:

On-screen controls are the game's, too. LineSweeper draws eight buttons once a finger has touched
the screen, asks each step which button every point is on, and feeds those into the same byte its
keys do, so a thumb resting on a button is a held key. Its
<RepoLink path="samples/linesweeper/README.md" hash="a-phone-held-upright">design notes</RepoLink>
say how, and how it lays itself out for a phone held upright. That layout has run only under
Chrome's device emulation and in a tall window on Windows, never on a real phone, and the
hosted demo gives a phone a poster and a recording of the game to tap and watch, not the game
itself, until real iPhone checks and the host page's phone layout pass. Android remains unverified.

## From a pointer to the world

A mouse position and a touch point are pixels, and what they land on is drawn in world
coordinates through a camera. `camera.world_position(point, viewport)` is the way back: the world
point under that pixel, seen through that view. LineSweeper's buttons ask it which board point a
finger is on:

<SourceFile
	path="samples/linesweeper/presentation/touch_controls.cpp"

With several views, which pane a pointer is in is the game's question: the call answers for any
pixel, inside the viewport or not, so a split-screen game picks the view first.
