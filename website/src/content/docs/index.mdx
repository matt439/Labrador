## Four choices, and what each one costs

<p class="lead">
Labrador is a small engine with firm opinions. Each one below helps some games and gets in the
way of others, so each comes with its price.
</p>

<div class="choices">
	<article class="choice" style="--choice-colour: #00f0f0">
		<h3>Ordinary C++ and standard tools</h3>
		<p>
			A game is a C++ program that links two static libraries. Its build file is plain CMake that
			names the sources, links the engine and puts the content beside the program, which is what
			building and running it needs; a release for players adds install rules. There is no project
			format, no code generator and no macro dialect between your source and the compiler.
		</p>
		<p class="cost"><strong>The cost:</strong> all behaviour is C++, and every change to it is a compile. There is no visual editor, no scripting language and no hot reload.</p>
		<p class="evidence"><a href="/why/#ordinary-c-and-standard-tools">The full argument</a></p>
	</article>
	<article class="choice" style="--choice-colour: #f09800">
		<h3>Your data, your lifetimes</h3>
		<p>
			The engine meets a game at a few small interfaces, and what stands behind them is the
			game's choice: one class per entity, or one object holding ten thousand particles in a flat
			array.
		</p>
		<p class="cost"><strong>The cost:</strong> storage and ownership are your decisions. The engine does not manage objects for you, and those interfaces are virtual calls.</p>
		<p class="evidence"><a href="/why/#your-data-your-lifetimes">The full argument</a></p>
	</article>
	<article class="choice" style="--choice-colour: #00d050">
		<h3>Built for local 2D games</h3>
		<p>
			A scene can be drawn through several cameras into several viewports in one frame, which is
			what split-screen is. Gamepads come with deadzones, press edges and menu navigation.
		</p>
		<p class="cost"><strong>The cost:</strong> online play and 3D are out of scope for good.</p>
		<p class="evidence"><a href="/why/#built-for-local-2d-games">The full argument</a></p>
	</article>
	<article class="choice" style="--choice-colour: #a830f0">
		<h3>Rules you can test without a window</h3>
		<p>
			The falling-block sample keeps its whole game in a library that links nothing from the
			engine, so its tests play complete matches with no window and compare them byte for byte.
		</p>
		<p class="cost"><strong>The cost:</strong> that separation is a design you choose and keep. The engine makes it possible; it does not make it automatic.</p>
		<p class="evidence"><a href="/why/#rules-you-can-test-without-a-window">The full argument</a></p>
	</article>
</div>

## What Labrador is not

<p class="lead">
Knowing these before you start will save you time.
</p>

- **Never an editor.** Content is JSON in a text editor; behaviour is C++ in your IDE.
- **Never a scripting language.** All behaviour is C++, and every change to it is a compile.
- **Never hot reload or reflection-driven property editing.** The loop is edit, build, run.
- **Never 3D.** Labrador is for 2D games.
- **Never online.** Play is local: alone, side by side or split-screen on one machine.
- **Not cross-platform yet.** Windows and a desktop browser only.
- **Not big yet.** A small community, no asset store, and a 0.x API.

If you need any of these, [Godot or Unreal](/why/#with-godot-and-unreal) is the better choice,
and the Why page compares them. The [design documents](/docs/design/) say where
Labrador is going.

</section>
