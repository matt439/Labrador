# Beginner guides: the audit of 2026-10-30 and its work list

This document owns TODO.md's `GUIDE#` rows. It records an audit of every
procedure the website publishes, read as the reader the owner set on
2026-10-30 ([BACKLOG.md, Decisions only the owner can make](product/BACKLOG.md#decisions-only-the-owner-can-make);
[PERSONAS.md](product/PERSONAS.md)): someone with very little programming
experience who wants to play around with Labrador. Terminal commands and
manual setup are acceptable, but every procedure has an exhaustive guide:
every command in a copyable block, what the reader will see, how long it
takes, what each failure means and how to recover. Experienced readers skip
the guides. Get Started, after OCA-78's starter ZIP, is the bar.

**Method.** Five readers each took a group of pages (Get Started, content and
assets, gameplay guides, shipping and the web, the front door and samples)
and listed every gap against that bar. A separate reader tried to refute each
blocker and major gap against the page, the components it renders and any
page it links; 86 survived and one was refuted. A completeness pass looked
for procedures nobody covered. Minor gaps were not individually checked.
Nothing was built or run for the audit; what it could not verify is listed
below.

**Verdict.** Only Get Started meets the bar, and its edit, build and run loop
still has holes. Elsewhere the guides read as reference for someone who
already edits C++ and CMake: fragments, "add a line beside the fonts one",
commands run "from the repository root", rarely what the reader will see or
what a failure means. Several assume a Git checkout that the starter ZIP
route does not give. Most of what a beginner would do to play around has no
guide at all.

## The engine inside a starter project

Checked on 2026-10-30 at commit `0690ffc` on the owner's desktop, for
`GUIDE#1`. `starter_zip.py` made `labrador-starter-dev.zip`, Windows' `tar`
extracted it to `C:\dev\g1\mygame`, and every command below ran in
`mygame\external\labrador`, which has no `.git`, from vcvars' environment
with every Git folder removed from `PATH`:

```bat
cmake --preset x64-debug
cmake --build --preset x64-debug
ctest --preset x64-debug
```

- The configure finished in 12 seconds. `source_revision.cmake` finds no
  `.git` marker and leaves the engine's revision `unknown` without asking Git.
  vcpkg restored every package from this machine's binary cache; on a machine
  whose cache holds only the starter's own packages, it also builds
  `lodepng`, which the engine's tests need and the starter's manifest does not
  list.
- The build of 326 steps took 26 seconds and all 20 tests passed in 30, the
  Direct3D pixel tests among them. `out\build\x64-debug` takes 1.0 GB.
- All six samples are under `out\build\x64-debug\samples\<sample>\`, with
  their content beside each `.exe`. Started from another folder, the minimal,
  collision, audio and local-multiplayer samples each passed `--smoke-test`
  with exit code 0; LineSweeper and the components gallery, which have no
  smoke test, opened their windows and stayed up until closed.
- Afterwards the starter game's own configure, build and tests in `mygame`
  were unchanged: `ctest -N` listed only `MyGameTests` and
  `MyGameSmokeTests`, and both passed. The engine's `out\` folder inside
  `external\labrador` is not part of the game's build.
- From the same prompt with Emscripten's `emsdk_env.bat` also run, the
  `wasm-debug` preset configured, built and passed all 32 tests in 137
  seconds, the six sample page tests among them; its pages are
  `out\build\wasm-debug\samples\<sample>\<Sample>.html` and the folder takes
  378 MB. Its configure prints three warnings from Emscripten that CMake
  4.3.1 does not support Emscripten shared libraries; the engine builds none.

These are times on a fast desktop, not on the low tier, and Git was hidden
rather than uninstalled. `GUIDE#4` and `GUIDE#7` can rely on this route.

## Findings

### Blockers and major gaps

Each survived a separate reader's attempt to refute it; severity is the one that reader assigned. Line numbers are as of the audit and drift as pages change.

#### `(no page)`

- **no guide, no line: Draw your own picture in the starter game (change or add a sprite), end to end.** sprites-and-text.mdx and assets.mdx give the texconv command and manifest/CMake rules as reference fragments. There is no single guided walkthrough for the starter project: download texconv.exe and where to put it (PATH or game folder), make game\content\textures, convert hero.png, add a textures group to manifest.json, add the copy_directory_if_different line (and the browser embed list), resolve the texture and draw it in hello_state.cpp, rebuild, see it, plus the errors ('... was never loaded', DX10 header refused, 'texconv is not recognized'). *Fix:* Write 'Put a picture in your game' at the Get Started bar, continuing from Make a first change.
- **no guide, no line: Add a sound to the starter game.** The audio guide explains banks against samples/audio and the sample README regenerates its own bank. No guide takes a beginner from 'I have a .wav' to hearing it in MyGame: getting xwbtool, the exact xwbtool flags (-f -nc required), manifest group, CMake copy line, resolve and play code, the XAudio2 endpoint requirement, and the browser first-gesture rule. *Fix:* Write 'Play a sound in your game' against the starter project with every command and edit, what you hear, and the failures by message.
- **no guide, no line: Add a new screen/state or a second level (new .cpp/.h files).** Nothing tells a beginner how to add a source file to the starter game. MyGame's sources are listed twice in game\CMakeLists.txt (EMSCRIPTEN block and Windows block), rules files go in MyGameRules, includes are written 'game/...', and forgetting the listing gives a linker error (LNK2019) that the troubleshooting page does not cover. concepts/states.mdx explains push/pop but is not a procedure. *Fix:* Write 'Add a screen to your game': create game\states\title_state.h/.cpp from a given template, list it in both blocks, push it from main.cpp, rebuild, and the errors. Add LNK2019 'unresolved external symbol' to troubleshooting.
- **no guide, no line: Add a moving or colliding object of your own to the scene.** Collision and local multiplayer guides explain samples; no guide adds a GameObject (e.g. a box the player bumps into) to the starter's HelloState, nor how to copy a focused sample into the starter project (the READMEs' 'What it borrows from outside this folder' is for experienced readers). *Fix:* A guided 'Add something to bump into' recipe in the starter, reusing collision sample code with exact files and edits.
- **no guide, no line: Read a build error you caused.** first-change.mdx:104 gives one sentence ('a typing slip'). troubleshooting.mdx lists environment errors by message but nothing on reading MSVC output: finding the first 'error C####' line with file(line), that later errors cascade, warnings-as-errors C2220, common beginner errors (C2065 undeclared identifier, C2143 missing ';', C1083, LNK2019/LNK2001, LNK1168 exe still running). Experienced users skip, beginners are stuck. *Fix:* Add a 'Reading a build error' page or troubleshooting section with an annotated real example and a table of the five or six common codes, each with cause and fix.
- **no guide, no line: Undo a change that broke the game (starter route, no Git).** Starter readers have no version control. Nothing tells them to copy the project before experimenting, or how to get one file back (re-extract it from the ZIP with tar to a scratch folder, or make a second project per starter.mdx 'A second project'). starter-to-git is optional and not offered as the undo answer. *Fix:* Add 'Keeping a working copy' to Get Started: an xcopy/robocopy backup box before experiments (excluding out\), and a box that restores one file from the ZIP. Point to Put your project in Git as the longer-term answer.

A beginner has never seen Ninja's failure output: a 'FAILED: game/CMakeFiles/...obj' line, a cl.exe command line several hundred characters long, then 'C:\dev\mygame\game\states\hello_state.cpp(81): error C2001: newline in constant', then 'ninja: build stopped: subcommand failed.'
